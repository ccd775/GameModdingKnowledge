# 尾巴等附属物：保留源形与局部修复

腰封上相互连接的蝴蝶结、绳带、刀饰需要共享来源锚点，而不是每件各取最高点。Karin Y曾因此出现前后/高度空隙；躯干修改后重新在腰封表面计算共同平移，保持整组源相对位置。具体判定及公式见 [上半身附件连接](UPPER_BODY_HANDS.md)。独立尾巴与腰封附件不自动共用同一锚点。

来自 PicodraTech Karin → Kitana tail-v2，再迁移到 Tanya / Li Mei / Mileena tail-v11。用户先确认 Kitana 正常，三角色同步修复后确认“看起来可以了”。这是当前可见尾巴效果验收，不代表新增了独立尾巴物理，也不覆盖所有动作/断肢。

## 核心区别：跟谁运动，与怎么改形状分开

源附属骨回退到某根原生人体祖先，是**动画绑定策略**；将顶点套入该人体区域的缩放/位移场，是**静止几何适配策略**。前者可用，不代表后者适用。

本案尾巴已经全部权重归于 Hips，中段仍扭曲：错误先发生在静止网格，而不是多骨混权重。骨盆高度过渡和骨段轴向缩放无差别作用到长尾巴，造成压缩、鼓起和曲线变化。只重刷权重或增加尾骨不会恢复已经损坏的静止源形。

排查顺序：锁定已安装版本 → 对照源/候选静止几何 → 检查局部尺度和连接位置 → 比较绑定/动作。只在动画中出现的问题再追踪权重、骨骼变换及物理；不能凭截图一律断言权重错误。

## 定位范围，不靠对象名称全选

1. 锁定源 Blend/FBX 的 SHA-256，核对活动形态键、骨架姿势和修改器。若源有非恒等姿势或拓扑修改器，先取得可对应的求值结果，不直接读取 basis 顶点。
2. 根据实际**正权重**识别尾巴骨家族，排除名字也含 Tail 的双马尾。本案为 `Tail_1..6`；挂带为 `Tail_Ribbon` 家族，二者不是同一个骨链。
3. 从正权重点扩展到经过审查的完整连通块，补足尾根只含父骨权重的顶点。扩展若进入躯干/其他物件，必须停下来重新划区域；不能把“整个连通块”当作无条件授权。
4. 验证边界没有未纳入的相邻边，并核对源/候选顶点顺序、拓扑对应。对象名、顶点数量一样还不够；旧 offset 清单只适用于完全相同的源和构建合同。
5. 附属物各自保留独立连接锚点。尾巴与下方飘带可以共同修复，但不必强行绑定同一根骨。

本例识别尾巴465点、飘带329点；仅看直接含 Tail 权重的444/317点会漏掉尾根。余下21/12个祖先权重点用于连接中心锚定。这些数量和名称都是案例值。

## 保持根部连接中心的统一缩放

当附属物应保留源曲线、方向和长宽比时，优先采用单一相似变换，而非逐骨段/逐高度变换。本案无需额外旋转：

```text
s_i = 源顶点（先统一到目标单位）
t_i = 旧候选中对应的连接锚点
k   = 已核实的统一体型尺度
A   = 经审查的根部锚点集合
d   = mean(t_i - k*s_i, i in A)
new_i = k*s_i + d
```

这保证根部锚点**中心**不移动，不保证每个根部顶点逐点不动。若接口必须逐点贴合，需单独设计根部过渡并审查边长/连续性，不能声称该公式保持了整个接缝。若确需旋转，使用整个附属物共享的刚性旋转 R，改为 `k*R*s_i+d`，记录 R 的依据。

本例 k≈1.500348，尾巴和飘带各自计算 d；新角色重新测量，不能复制相同坐标或比例。不得为了保住尾尖位置而让尾根与身体脱离。

## 应当留下的证据

- 修前局部边长比：尾巴约0.4336–1.8288，飘带约1.4812–3.1434；修后约1.50034，与统一尺度一致。不能只量总高度或包围盒。
- 检查完整相似变换的坐标残差、侧面曲线、尾根接口。边长一致本身不证明没有镜像、方向错误或曲面弯折。
- 根部中心误差本案 <0.00002 cm；794个点之外46,258个点及全部UV、权重不变。骨架、拓扑、材质槽也列入禁止变化范围。
- FBX在同世界轴下测试屈膝、脚踝、前臂/手部共25姿势；数值一致只证明导出未引入漂移，不等于这些动作全部在游戏验收。
- 从最终游戏容器重新导出网格，验证新几何与骨架。四个目标最大位置误差均 <0.0001 cm；显示顶点可因UV/法线拆分多于源顶点，不能直接把计数差判作重复网格。
- 记录真实用户反馈、版本和安装哈希。不要改写旧离线报告里的 `runtime: untested` 冒充测试；追加新的验收清单。

## 跨角色同步及增量打包

先在一个明确目标验证，用户授权后再推广。复用源形策略和源码审计，不复用第一个角色的骨架、包ID或body chunk。此案四个目标的新尾部坐标恰好相同，是测量结果，不是以后必须相同的断言。

每目标基线独立：Mileena必须用包含脸/面罩隐藏的v10，而不能退回v9；其余三者各保留自己的最新稳定包。只Cook新body，进行单export兼容处理，再移植到对应完整基线。未修改的多export头部包和store必须保留。严格只允许body/header变化，不重新生成纹理来“顺便统一”。

Kitana保留38个非body chunk；Tanya8、LiMei7、Mileena11，均逐字节不变。全部候选通过再批量预检，各自整套备份后逐组安装；批量部署不是跨文件原子事务。独立角色任务的其他更改不能被一并回滚。

## 脚本边界与后续改进

本机案例脚本按阶段为源范围审计、局部改形、FBX/姿势检查、body-only Cook/移植、最终容器回读和带备份部署；具体脚本/命令在本地 `TAIL_V11_NOTES.md` 和工程清单，不随便携指南分发游戏或模型数据。

现有 `fix_source_tail.py` 仍锁定Picodra源、固定数量、已知源offset及v11输出路径，**不是任意头像一键修尾工具**。`deploy_tail_v11.ps1` 只接受旧v9/v10作为首次迁移基线；安装v11后再次运行被拒绝是正常保护，不要删除断言。新版本须新目录、新清单、重新测量和验证。

本次尾巴仍跟随Hips、飘带跟随Spine，没有恢复源的独立多段动力学。若用户以后要求摆动、碰撞或独立尾骨，需要另立范围重新设计和验证；不得把本次曲线恢复称为完整动态移植。
