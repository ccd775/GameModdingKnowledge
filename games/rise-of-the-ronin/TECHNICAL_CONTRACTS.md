# 技术合同（build 20673762）

标注说明：`[I]` = 引擎/格式不变量；`[B]` = 随 build 变化；`[C]` = 本案例数值。

## 1. 加载器

- `[I]` ROTR Mod Loader（Nexus Mods `riseoftheronin/mods/9`，1.0 版，2025-03 的文件）由两部分组成：游戏根目录的 `dinput8.dll` 代理，以及 `RONPATCHER/` 目录。
  - `RONPATCHER/root/` 下按哈希命名的散装文件（`0x<8 位十六进制>.g1m/.g1t`）会覆盖资源表里的同名资源。
  - `RONPATCHER.ini`、`Patches/`、`system/` 是加载器自己的配置。mod 包里不要带，以免覆盖玩家设置。
  - 加载器压缩包里还附带 `g1ttools`（`g1t_extract.exe` / `g1t_replace.exe`）和 `qrdbtool`，它们是独立工具，和加载器本身无关。
- `[I]` `RONPATCHER.ini` 设置 `log_external=true` 后，每次启动会重写 `RONPATCHER/patcher_log.txt`：
  - 每个 root 文件对应一行 `... added to virtualization`，可以据此确认文件被加载器接管；
  - `Open 0x<hash>.<ext> (pkg=...)` 行**不完整**：651、8DC、D462 和捏脸头从来不出现。它们只能作线索，不能证明某个文件没被用到。
- `[I]` 散装文件比原资源大也没关系。
  - 曾把头模型（是原版的 2.25 倍）改走社区做法：新建 fdata、改 RDB 记录、加 RDX 槽。渲染结果与散装文件完全相同，之后已撤回。
  - 社区 mod 的覆盖文件都比原资源小，这只是巧合，不是要求。

## 2. 资源表与 fdata

- `[I]` 游戏数据目录是 `fdata_package_dx12`：`root.rdb`（条目）+ `root.rdx`（fdata 序号 → 包哈希）+ `0x<hash>.fdata`。
- `[I]` `root.rdb`：
  - 文件头 `_DRK`，+8 处是第一条记录的偏移；记录按 4 字节对齐。
  - 每条记录：`IDRK`；+8 u64 记录大小；+0x10 u32 尾部大小（`0xD` 或 `0x11`）；+0x18 u64 文件大小；+0x24 起依次为 u32 文件哈希、类型哈希、flags。
  - 尾部：u16 标志（`0x401` = 位于 fdata 内）、偏移（`0x11` 型多一个高位字节，共 40 位）、u32 完整大小、u16 fdata 序号。
  - 全部 60769 个 G1M 记录的依赖块都是同样的 5 个哈希。这是类型描述，不是材质绑定。
- `[I]` `root.rdx`：8 字节一条：u16 序号、i16 −1、u32 fdata 包哈希。
- `[I]` fdata 条目：
  - 结构：`IDRK0000`；3×u64（条目大小、存储大小、解压后大小）；4×u32（种类、名称哈希、类型哈希、flags）；元数据；载荷。
  - 存储大小等于解压后大小时，载荷是原样存放的。
  - 否则是 zlib 分块：flags 含 `0x100000` 时每块前有 u32 长度；不含时每块前是 u16 长度加 8 字节。
- `[I]` 类型哈希：G1M `0x563BDEF1`；G1T `0xAFBEC60C` / `0xAD57EBBA`；KTID `0x8E39AA37` / `0xBE144B78`；kidsobjdb `0x20A6A0BB`。
- 便携包 `ktdata.py extract` 按哈希取出资源，命名方式与 `RONPATCHER/root` 一致；G1H 也存成 `.g1m`，这个命名已在实机上生效。

## 3. 贴图槽的解析链

- `[I]` G1M 材质里每个槽记录 `(index, layer, type, subtype, tile x, tile y)`。
  - `index` 是 KTID 表的槽号。KTID 载荷是 `(槽号, kidsobjdb 对象)` 对；对象的第一个值就是 G1T 哈希。
- `[I]` 模型 → KTID 的关系存在 CharacterEditor kidsobjdb（`0xB290631C`）里：
  - 先找到第一个值等于模型哈希的条目；
  - 它的单值整数属性引用其他条目，被引用条目的第一个值就是 KTID 资源。
  - 便携包用 `ktdata.py slots` 列出一个模型的整张槽表。
- `[I]` 运行时还有 **TextureAlias**（D956 表，每张 8 槽：0 COLOR、1 SHADING、2 NORMAL ……），会把静态槽表重定向。
  - `[C]` 下身走 `D956E4A2` / KTID `7934D55A`：COLOR `C946E4AF`、SHADING `76C5CE28`、NORMAL `B406343D`。上身走 `4230A92D` 那张表。
  - 静态 KTID 表把 651 可见上身的 COLOR 指向 PicodraTech 图集 `0x120A5B1F`，但运行时被 alias 改走了。只看静态表就去重画这些图集是错的。
- `[I]` 对象库 `0x2082AD97` 记录装备部件：
  - 类型 `0xD186CEEB` 的条目带 UTF-8 名字，属性 `0xB3A1E5AA` 是槽位类型。
  - 槽 25 是脸，名字形如 `Face_000x / Eye_L_000x / Baked_000x`；槽 5 是基础身体；槽 2 是铠甲（651、8DC）。
  - 脸条目的属性 `0x68A6F779` 指向 `0xC4B9B28D` 部件，后者的属性 `0x0B6E1578` 指向 CharacterEditor 模型信息，其第一个值是 G1M 哈希。

## 5. G1M

- `[I]` 文件头 `_M1G` + 4 字节版本；+8 文件大小，+12 第一个块的偏移，+20 块数。
  - 块的魔数按小端存储，例如 `GM1G` 就是 G1MG。651 / 8DC 的块：FM1G、SM1G、MM1G、GM1G、LLOC、ONUN、DILF；4BA 没有 LLOC / ONUN，多一个 RTXE。
- `[I]` GM1G 的分节：
  - 共 9 种：GEOMETRY_SOCKETS、MATERIALS、SHADER_PARAMS、VERTEX_BUFFERS、VERTEX_ATTRIBUTES、JOINT_PALETTES、INDEX_BUFFER、SUBMESH、MESH_LOD；
  - 字段布局与 gust_stuff v1.3.13 的 `parseG1MG` 相同；
  - 版本大于 `0x30303430` 时，顶点缓冲和索引缓冲的头多一个 u32。
- `[I]` 子网格是 14 个 u32：标志、VB、调色板、骨、未知、shader、材质（texture set）、IB、未知、图元（3 = 三角形列表）、VB 起点、顶点数、IB 起点、索引数。
  - **索引是相对整个 VB 的绝对值**，共用 VB 的子网格各占一段。
- `[I]` 调色板条目 `(G1MMIndex, physicsIndex, jointIndex)`：
  - `jointIndex` 是**骨号**；
  - G1MS 的 id 表把骨号映射到骨架存储序号，二者不同：4BA 有 197 个关节，651 和 8DC 各 589 个，D462 557 个，捏脸头 507 个，全都不是恒等映射；
  - gust 的 `bone_<n>` 用的也是骨号；
  - 顶点里的骨索引 = 调色板下标 × 3。
- `[B]` 651 下身 VB（stride 60）：
  - POSITION f32×3 @0；BLENDWEIGHT0 f16×4 @12；BLENDWEIGHT1 f16×4 @20；BLENDINDICES0 u8×4 @28；BLENDINDICES1 u8×4 @32；
  - NORMAL f16×4 @36；TEXCOORD0 f16×2 @44；TEXCOORD1 f16×2 @48；TANGENT f16×4 @52。
  - 原版缓冲的 stride 在 36 到 56 之间，有的 BLENDWEIGHT1 只有两个分量（存 6 个权重，其余取余量）。按 VERTEX_ATTRIBUTES 读，不要写死。
- `[B]` 索引宽度要从分节里读：651 上衣是 R16，8DC 上衣是 R32。
- `[I]` gust 导出会丢掉没被索引引用的顶点，所以它导出的 VB 不能当作 G1MG 里的原始字节去替换。
  - 20261004a 的 651 经 gust 往返后，从 2,423,988 字节变成 2,332,980 字节，顶点与权重读回一致；不改任何东西时往返是否逐字节一致没有测过。
  - 便携包的 `leg_weights.py` 改为原地写入：只有改到的混合字节、调色板、MM1G 和 FM1G 计数会变。

## 6. 骨架、绑定与权重

- `[I]` SM1G：
  - +12 关节数据偏移，+20 关节数，+22 id 表长度，+28 起是 id 表；
  - 每个关节 48 字节：缩放 3f、父关节（存储序号）、旋转四元数 xyzw、位置 4f；
  - 世界变换为 `q_world = q_parent · q_local`，`p_world = rotate(q_parent, p_local) + p_parent`（不含缩放）。
- `[I]` MM1G：
  - +12 矩阵数，+16 起每个 64 字节，行主序；
  - 原生条目满足 `MM1G = inv(world).T`，即左上角是 R，最下一行是 −Rᵀp。
- `[I]` FM1G +24 是 MM1G 的矩阵数。追加绑定时两处一起加（写之前先核对两者相等）。
- `[C]` 原生程度：
  - 4BA 有 298 / 398 个调色板条目是原生的，例外是 147–152 等辅助骨；
  - 绑腿 87/88 有 0.007 的误差；324 的第 2、3 个调色板（各 4 根骨）误差约 51，属于另一种约定；
  - 模板（Picodra 20260916a）里只有约三分之一的条目是原生的（651：80 / 267，8DC：84 / 242）。其余是重新校准过的手指，以及扭转和布料辅助骨，误差最大 59（651）和 69（8DC），所以不能直接用离线 FK 摆模板的姿势。
- `[C]` 女性骨架（651 / D462 共用）的骨号：
  - 坐标：髋 2 为原点，Y 朝上，+Z 朝前，+X 是角色左侧；手臂约 15° A 字姿势；
  - 躯干：髋 2、脊柱 9、胸 10 / 11、颈 12 / 13、头 14；
  - 手臂：肩 15 / 16、上臂 17 / 18、前臂 19 / 20、手腕 21 / 22，五指在 27–64；
  - 腿：大腿 3 / 4、膝 5 / 6、脚 7 / 8、脚尖 25 / 26；
  - 腿部辅助骨：85 / 86、87 / 88、89 / 90、91 / 92、93 / 94、111 / 112、129 / 130、133 / 134；
  - 前臂辅助骨：103 / 105 / 131（左）和 104 / 106 / 132（右）。
- `[I]` 顶点着色器（`shader_dx12/0x00b6c7f0.file`，用 dxc 反汇编）在 8 骨模式下：
  - 只读前 7 个显式权重，第 8 个影响取 `1 − 前 7 个之和`，最后把 N / T 归一化；

## 7. 捏脸头 G1H

- `[I]` `_H1G` 容器里约有 41 个嵌入的 G1M，只有最大的一个带几何。
  - 它有 38 个子网格：0–7 是头和脖子的皮肤（女性头顶 y 78.0，脖子下到 y 47.2），其余是眼睛、睫毛和牙齿。
- `[I]` 它的骨 11–14 与 651 / D462 相同，所以网格已经在 651 的空间里。
- `[I]` gust 对它报 "not G1M!"，要先切出最大的 `_M1G`（大小在 +8）。便携包的 `g1m_tool.py` 能直接处理 G1H。
- `[C]` 清空方法：把每个子网格的所有索引改成该子网格的第一个索引，长度不变、G1H 内偏移不变。
  - 以 `0xb24cac84.g1m` 放进 root，2026-10-01 实机确认原头不再显示。
  - 副作用：不戴头巾时角色没有头。
