# 材质与贴图

标注同[技术合同](TECHNICAL_CONTRACTS.md)：`[I]` 不变量、`[B]` 随 build 变化、`[C]` 本案例数值、`[H]` 推测。

## 1. G1T 容器与存储

- `[I]` 结构：`GT1G` + 版本；+8 文件大小，+12 偏移表位置，+16 贴图数；每张贴图有 8 字节头，可能跟着额外头，然后是数据。
  - 8 字节头：第 0 字节高 4 位是 mip 数、低 4 位是贴图系统；第 1 字节是格式；第 2 字节是 log2 尺寸（高 4 位高度、低 4 位宽度）；第 7 字节非零表示有额外头。
  - 额外头：+0 是额外头大小；+8 u16 是图层数 << 4（只在系统 3 时有效）；**+10 是存储标志**；+12 / +16 是宽 / 高（额外头足够长时）。
  - 格式码：`0x59` / `0x06` BC1、`0x5B` BC3、`0x5C` BC4、`0x5D` BC5、`0x5E` BC6H、`0x5F` BC7、`0x02` R32_FLOAT、`0x04` R32G32B32A32_FLOAT。
- `[I]` **存储标志 1 = DX12 64 KB tile**：
  - 每个 tile 是 64 行块，每行 1024 字节，所以 BC1 / BC4 是 128×64 个块，BC5 / BC7 是 64×64 个块；
  - 不超过 64 KB 的 mip 仍是线性的；
  - 所有处理都要按每级 mip、每个图层分别计算。
  - 数组贴图的载荷是一条 mip 链的整数倍（遮罩槽的 BC7 有 3 个图层）。只解码第 0 层的工具会看漏后两层。
- `[I]` 把 tiled 载荷当线性读，会看到「左右两半互为副本」的图。
  - 早期的「头部图集折叠不变量」和「运行时在 u 和 u+0.5 各采一次」两种理论都由此而来，已撤回。
  - 直接把存储标志清零、不重排载荷，实机会出现粉色图集块。
- `[I]` 实测发现：游戏自己的 BC 贴图 mip 一直做到 4×4（1024 → 9 级，2048 → 10 级）。
  - 上游 mod 有 6 张贴图只有 1 级 mip，但对应槽声明的是 9–10 级（包括 SHADING `0xE516941C`）。补齐后有 5 张与原版字节数一致。
  - 补齐 mip 修好的是远处闪烁，不是头部脏污：A/B 差异 3.95，低于 5–7 的抖动底线。
  - 四张旧身体 COLOR 的 mip0 正常，后面几级与 mip0 对不上（第 1 级与正确下采样的 MAE 为 48.92，重建后为 2.78）。不能只看最高一级。
- 便携包：
  - `g1t_tool.py info / dds / storage / mips` 负责读取、导出、存储方式互转和 mip 检查。
  - 解码交给 texconv：`dds` 先套上 DX10 DDS 头，并按存储标志还原 tile。

## 2. 槽位语义（材质里的 `type`）

| 类型 | 含义 | 依赖 UV 布局 | 备注 |
| --- | --- | --- | --- |
| 1 | COLOR | 是 | 头部只有 `0x97338C5A` 这一个颜色来源（整头填洋红后，头整体变成纯色） |
| 2 | SHADING | 原版有细节 | BC5 / BC1 / BC7，各通道含义没有完全查清，见 §4 |
| 3 | NORMAL | 是 | 缺了覆盖时，会透出原版服装的浮雕杂纹 |
| 5 | DIRT | 常量为主 | 1102 个角色模型的 DIRT 槽用全局默认值 `0x1E76FD2D`（1×1 R32F = 1.0） |
| 24 | 256 px 平铺细节 | 平铺 | `0xDEB69BD0` 有 62 个角色模型共用 |
| 其他 | 未命名 | — | 用 `ktdata.py slots` 列出后逐个核对 |

- `[C]` 在同一个材质图层里，遮罩槽在游戏原数据中的 **R 通道总是 255**：
  - `0xF311E1FA` 就是常量 `(255,255,0)`；
  - `0x6BFBA678`、`0x982D580E`、`0xDBB875CF` 的 R 为 255，只有 G 通道有细节；
  - BC4 的 `0x3C82D5D7` / `0xB42B5209` 为 174 / 255。
  - 上游 mod 在这 6 个槽里放的是纯黑，其中四张 BC7 彼此逐字节相同，所以至多有一张是对的。遮罩为零是唯一可能把整层材质关掉的改动。

## 3. 共用贴图：最危险的一类错误

- `[I]` 替换服装时覆盖的贴图哈希，其他模型往往也在用。一张贴图 = 一个哈希 = 全游戏一份。
- `[C]` 上游 KarinMod 把许多覆盖都做成了常量，Picodra 和 Original 两条线一直沿用。2026-10-04 对比全游戏的 KTID 表后，发现 13 张必须恢复原版字节：

| 贴图 | 为什么必须是原版 |
| --- | --- |
| `0x1E76FD2D` | 全局 1×1 R32F 默认值（1.0），1102 个角色模型的 DIRT 槽在用。上游改成了 0，NPC 的身体、手、腿、牙齿因此发白发亮。两版文件只差 +0x3A / +0x3B 两个字节 |
| `0xDEB69BD0` | 62 个角色模型共用的 256 px 平铺细节；Karin 下身也用，恢复后多了原版的细微纹理 |
| `0x26871FC4` `0x3D1F0629` `0x982D580E` `0xBE05AF5C` `0xC3989E0F` `0xE9E4455D` | 8DC 的 texture set 1 只用于隐藏的子网格；另有 1 个模型在用 |
| `0x1E809902` `0x4DADDD16` | 651 的 texture set 2 只用于隐藏的子网格；另有 6 个模型在用 |
| `0xD4824BF5` `0xE516941C` | C097 头盔模型 `0x3B6EAD06` / `0x666BBE1F` |
| `0xC29D729F` | 不是 Karin 头部的副本，Karin 的材质没有绑定它 |

- `[C]` 奇兵队制服（6 个 NPC 模型）和 Karin 下身的 alias 表共用 `0x8B3916E2`。
  - 上游把它从 BC5 改成了 BC1 常量 `(8,77,255)`；现在改回 BC5，取原版均值 `(32,129)`。
  - 用常量而不是原版字节，是因为 Karin 的 UV 和原版布局不同。
- `[I]` 判断方法：
  1. 用 `ktdata.py usage --mod-root <root> --own-models <被替换的模型>` 列出每张覆盖贴图还有哪些模型在画；
  2. 改了、又被别的可见模型使用的贴图，排在报告最前面；
  3. Karin 可见部分不用、只有别人在用的，恢复原版字节；Karin 也用的，看 UV 是否依赖布局，再决定用常量（原版均值）还是重烘焙。
  - 静态 KTID 扫描不包含 TextureAlias 表，alias 的用途要另查。

## 4. 常量贴图与 SHADING

- `[I]` 常量写法：
  - 每级 mip、每个图层都填同一个块，容器不变（头、尺寸、格式、mip 数、文件长度都不变）；
  - BC1 用两端点相等、索引全 0 的块；BC4 / BC5 用每通道两个相同端点；BC7 用 mode 6、两端点相等、索引全 0；R32F 直接写浮点。
  - 常量与 UV 无关，换到新网格上只会改变亮度，不会带进原版布局的图案。
  - 便携包 `g1t_tool.py constant` 写出的结果，与 2026-10-04 发布的 5 张修复贴图逐字节相同。
- `[I]` texconv 默认把平法线编成 BC1 时会偏成 `(132,130,255)`。要么用 BC7，要么手写 BC1 块。
- `[C]` 上身之所以正常，是因为 4BA 的 49 个槽里只有 1 个被覆盖，SHADING 仍是原版的。下身那几个模型的槽几乎全被覆盖，而上游的 BC5 SHADING 一律是常量 `(8,77,0)`；原版同槽的 G 通道在 120–185 之间，有细节。
- `[H]` **下身 SHADING 的 G 通道越低，表面越亮、越「光滑」**：
  - 20260908b 为了提亮腿套，把 `0x76C5CE28` 的 G 从 77 降到 8，当时用户认可了亮度；
  - 之后用户报告冷启动亮度不稳，以及某些天气、时间下半身变暗、变红；
  - 推测原因是 G=8 接近镜面，会映出天空颜色。20261004a 把 4 张 SHADING 改为原版逐通道均值，如 `(8,150,232)`。
  - 这一条尚未实机验证。如果用户再嫌暗，应该提亮 COLOR，而不是再降 G。
- `[C]` 其他实测：
  - 直接照搬上身的 `(8,8,8)` 会更黑；
  - 加大 R 会出现强高光；
  - 清零下身 shader 块 2 的 `vDt2Bld` 后更暗（已撤回）。
  - 不要猜测通道语义，按原版均值走。

## 5. 颜色贴图与改色经验

- `[C]` **头部图集 `0x97338C5A` 是 D462 唯一的 COLOR 绑定。**
  - `0xC29D729F` / `0xD4824BF5` 在 D956 alias 表里，读的是图集右半边；
  - v1.8.0–1.8.2 为了守一条旧的打包规矩，把重建后的 973 镜像进这两个文件；右半边一放头发，脸就出现蓝白条纹，上身错乱、下身变暗、尾巴变成深蓝。
- `[C]` **头发「脏」**：
  - 对照原版白发主角，mod 的色度噪声并不比原版高，但亮度细节只有原版的 0.36–0.47 倍。原版靠发丝明暗把颜色差异盖住了，近乎平涂的白发盖不住，每个 UV 岛的色偏都显成斑块。
  - 所以修法是恢复发丝明暗，而不是继续抽掉颜色：
    - 色度 ×0.35；
    - 按源图做单调直方图匹配：中位数和 p95 都对上源图，统一增益会把真正的点缀色一起压掉；
    - 锐化要加限幅。
- `[C]` 两次自己造成的回归：
  - 不加限幅的锐化在岛边缘冲过了 254 个亮度单位；
  - 不限范围的死区填充，把均匀的死区变成了 Voronoi 拼块，硬边一直留到 mip 里。
  - 实机头上因此出现深色条纹，而「色度 / 亮度比」指标反而变好了，因为条纹是亮度。这个指标会被亮度伪影骗过，必须同时看渲染和 mip-3 的统计。
- `[I]` **给某个部件改色时按几何选，不按色相选**：
  - 图集里不同部件共用颜色，按色相选曾把青色带到耳朵上；
  - 按连通分量选岛，加 1 像素外扩：覆盖 95.2%，溢出 128 像素；外扩 3 像素溢出 1088 像素，覆盖只多 2.7 个点。
- `[C]` 源美术才是基准：
  - 源图里白发的刘海没有一点蓝色，只有两根尾巴的系带是青色；
  - 发布图集里大面积的蓝色是管线造成的损伤。
- `[C]` 背部标志错乱：
  - 原 mod 的标志在无光照渲染里就是乱的，不是光照或 mip 的问题；
  - 从源材质局部重烘焙到现有 UV，其余区域放大时保留原色值和各级压缩块。
- `[C]` 鞋袜局部重烘焙：
  - 先在 2048 空间重烘约 9% 的图集，保护没有映射或 UV 冲突的区域；
  - 再回到已认可的 1024 BC1 容器，只替换局部压缩块。
  - 2048 BC7 和 2048 BC1 两个候选都比认可图暗，被拒绝。原生格式、离线像素接近，都不能证明适用。

## 6. 诊断探针

- `[I]` 实机探针贴图可以回答「谁在画这张贴图」：
  - 整张填洋红：出现洋红的地方就是它的消费者；完全没有洋红只能记为「未定」，可能是遮挡或混合。
  - 16×16 标签网格：读出 UV 对应关系；1 m 和 3 m 两个距离的读数必须一致。
  - 探针包相对基线只改一个文件。
- `[I]` 帧捕获走不通，详见[排障手册](TROUBLESHOOTING.md)：游戏通过 NVIDIA Streamline（`sl.interposer.dll`）创建 D3D12 设备，RenderDoc 的钩子虽然装上了，却抓不到帧。PIX 没有试过。
