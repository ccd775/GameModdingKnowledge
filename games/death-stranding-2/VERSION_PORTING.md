# 跨版本移植（1.0.48.0 → Steam 1.10.89.0）

mod 是在 1.0.48.0 上做的。Steam 版更新到 1.10.89.0 后，发行安装器按设计拒绝安装（一位玩家报告：16 个组里 12 个对不上）。本页记录怎么判断两个版本差在哪、怎么不重做 mod 就把发行包移植过去，以及以后游戏再更新时的做法。

证据边界：1.10.89.0 的结论来自本地一份 Steam 正版（2026-11-16）；两版的差异是 `build-sensitive`，方法本身是 `case-derived`。

## 1. 两个版本差在哪

| 项 | 1.0.48.0 → 1.10.89.0 |
| --- | --- |
| 流图类型哈希 | 相同（`929D7AF6A30CD1C5`），布局不变 |
| 类型表 | 多 2 个类型（共 4764 个），Odradek 1.0.49.0 的 `types_1048.json` 里没有 → `graph.py` 把未知类型记成 `Unknown_<哈希>`，不影响 mod 用到的组 |
| 组 | 多 6 个组，**大部分组号后移**：50108 → 50109、50109 → 50110、50110 → 50111、50113 → 50114、50116 → 50117、50120 → 50121、50121 → 50122、31123 → 31126、31225 → 31228、6744 → 6745、12706 → 12712、58946 → 58950、67632 → 67638、67673 → 67679、67695 → 67701、67696 → 67702、67699 → 67705、67704 → 67710、67706 → 67712 |
| mod 涉及的组 | 对象数、组大小、类型序列、span / locator / 链接记录的条数都不变 |
| 组里的数据 | 只改了几类字段：`ShaderResource.Unk14`（16 字节着色器 ID，着色器重编译）、`ShaderFromFileResource.Unk14`、`LodMeshResource` 的 `RuntimeMeshes[].Distance` 和 `SkinnedLowDetailFirstLodIndex`、`RenderEffectResource` 的 `TextureBindings[].PackedData`（见 [材质与磨损](MATERIALS_AND_WEAR.md#5-贴图绑定的-packeddata)），31123 里另有 2 个 `CameraActorResource.ExcludeFromPlacementPrediction` |
| 字节数 | mod 替换核心的组里：50108 511 字节、50110 252、50113 204、50120 359、67704 16，其余 0；31123 有 602 / 48074 个对象变了（5239 字节，mod 不替换它的核心） |
| 链接表 | 每组记录条数和顺序相同；按组号写的记录（`StreamingRef`）随组改号 |

所以安装器拒绝是对的（组号和指纹都变了），但 mod 本身不需要重做：组的结构没变，只要把组号、指纹、链接记录换成新版的，把新版自己的那几处改动合进 mod 替换的核心里。

判断用的工具：`mapgroups.py`（组对应 + 每组的数据 / locator / 子组 / 链接核对）和 `corediff.py`（同一组在两版间逐对象、逐字段比较，按“类型.字段路径”汇总）。

## 2. 旧版原始数据从哪来

移植要三方比较：旧版原版（v0）、新版原版（v1）、mod（m）。1.0.48.0 的游戏副本后来删掉了：

- 干净根目录里顶层的包文件是硬链接，原游戏目录删了照样能读；子目录（如 `l100_mex`）是目录联接，失效了（6744 的旧核心读不出来）。
- 读不到的组，用旧版收集报告里每个 span 解压后的 SHA-1 代替（`known`），足够判断“数据是否相同”。
- **`ds2_pc_mi` 导出的 `.core.pristine` 不是原版。** 和原版 span 比，10 份里 9 份有 1–832 字节不同（工具重写过），不能当 v0。最初按它合并，50108、50110、50113、50120 都报“不是原版数据”；改成读旧版自己的文件、并用报告的 SHA-1 核对。

## 3. 组对应（`mapgroups.py` 的 `build_map`）

- 键：`(NumObjects, GroupSize, TypeCount, 类型哈希序列, 根对象 UUID)`。键唯一就直接对上。
- 新版里根 UUID 变了的组（6744 → 6745）用不含根 UUID 的后备键。
- 多个组同键（小的变体组）时依次用：解压后的对象数据（SHA-1）、已对上的子组、附近组的组号偏移。
- 结果：mod 的 manifest 涉及的组和它们的子组共 726 个，713 个对上；没对上的 13 个都是子组，键或数据在新版里变了（指向它们的多是材质的 `Shader`、`TextureResource` 字段）。mod 改过的记录都不指向它们（否则移植会报错停下）；原版记录指向它们的地方，新版的原版记录本来就指向新组。
- 坑：`Graph.links(gi)` 会一直读到整张链接表的末尾，比较单组的记录要在 `LinkStart + LinkSize` 处截断（`group_records`）。第一次核对没截断，记录数全对不上。

## 4. 移植发行包（`port_release.py`）

输入是一个发行变体目录（`manifest.json` + `karin.core.stream`，`make_release.py` 生成）。输出 `manifest_<版本>.json`：同一个包文件，加上安装时要打的字节补丁。

1. **组改号、指纹取新版**：NumObjects … LocatorCount、类型 SHA-1、子组号、组链接 SHA-1 都取新版的值；类型序列必须和旧 manifest 的相同。
2. **span / locator 按序号对应**：映射后的组 span 长度、locator 个数相同，mod 的重定向原样沿用。
3. **核心三方合并（`merge_span`）**：逐字节比较 v0 / v1 / m。v0 ≠ v1 且 m = v0 的字节取 v1（新版自己的改动），写成 `archive_patch`（`[{offset, hex}]`，按包文件偏移）；v0 ≠ v1 且 m ≠ v0 是冲突，停下不出 manifest。另记 `patched_sha256`（打完补丁后的包）。
4. **链接补丁按记录序号重编码**：mod 改过的每条记录，在新组链接表里取同一序号的记录。先核对两版原版记录的目标映射后相同，再把 mod 的目标换成新版的（本组：同一下标；子组：它在新子组列表里的位置；`StreamingRef`：新组号），按新记录的长度编码。
   - 坑：组字段的值很小时，既可以是子组位置，也可以是 `StreamingRef` 的组号（比如 31123 的一些记录同时“像”子组 67690:0 和组 160）。用 `relink.py` 的 `TracingReader` 解析新组对象到那条记录，看字段类型是不是 `StreamingRef`。
5. 任何一项不符（组没对上、长度变、冲突、记录对不上）都列出来并退出，不写 manifest。

v35 的结果：

| 变体 | 组 | span | locator | 链接补丁（按记录） | 核心补丁 |
| --- | --- | --- | --- | --- | --- |
| 无表情（v34） | 16 | 10 | 174 | 150 | 85 段，983 字节 |
| 有表情（v35f） | 19 | 12 | 187 | 176 | 234 段，1342 字节 |

`make_release.py` 的“链接改动”按字节段计数（v34：107 处），这里按记录计数，两者不能直接比。

## 5. 离线核对

- `port_verify.py`：在内存里按新 manifest 安装到新版流图和链接表上（与安装器同样的改法），读出每个被改的组，和原 mod 构建逐对象比较：指针必须指向映射后的目标；不一致的指针按“目标组在新版里有没有对应”分成 `changed`（目标是数据变了的组，原版记录本来就指向新组）和 `SUSPECT`。v34 和 v34f 的移植都没有 `SUSPECT`；6744 的旧核心读不到，只确认了新版能整组读通（653 个对象）。
- `port_fields.py`：逐字段三方核对。v0 = v1 时安装结果必须等于 m；m = v0 时必须等于 v1；否则算冲突。
  - 有表情版（v34f 的全部替换核心的组，加 v35f 的 50120）：0 处不符、0 个冲突。两边都改过的对象：50110 的 3 个效果（mod 的腐蚀变量改名 + 新版的 PackedData，互不相干）；v35f 的 5 个脸部效果（v14f 的贴图重指 + 新版的 PackedData）。
  - 无表情版（v34）：没有跑逐字段核对（远端连接中断，机器让给了别的工作）。覆盖它的是 `merge_span` 的逐字节冲突检查（0 个冲突，否则不会出 manifest）和上面的 `port_verify`（没有 `SUSPECT`）。
- 回归：重构 `port_release.py`（抽出 `merge_span`）后重新移植，输出的两个 manifest 与发行的逐字节相同。

## 6. 安装器：一个变体多个 manifest

发行包每个变体目录里放 `manifest.json`（制作版本）和 `manifest_<版本>.json`（移植版）。安装器：

1. 按名字读全部 `manifest*.json`，和 `DS2.exe` 版本相同的排在前面；
2. 逐个核对（同第 1 版的逐组核对），第一个全部通过的就用它；全都不过就列出第一个的不一致项、提示运行收集工具，不写任何文件；
3. 移植版先把包文件复制成临时文件、打 `archive_patch`、核对 `patched_sha256`，不对就删临时文件退出；之后才备份并改游戏文件。`state.json` 记 `game_build`。

测试：

- Steam 1.10.89 流图 / 链接表的副本上，两个变体安装、互相切换、卸载往返；装出的流图（SpanTable、LocatorTable、Groups）、链接表、包文件与离线模拟逐字节相同，`patched_sha256` 相符；卸载后与原版哈希相同。
- 1.0.48 流图上（放一个 1.10.89 的 `DS2.exe` 让它先试移植版）：两个变体都回落到 `manifest.json`；无表情版装出的流图仍是旧安装器的 `F1020727…`，包文件与发行的相同。
- 仓库测试 `test_ds2_release_installer_picks_the_ported_manifest`：合成流图里组改了号，`manifest.json` 不通过、移植版通过，补丁后的包正确；`patched_sha256` 错时不写任何文件、不留临时文件。

## 7. 实机（agent，2026-11-16，Steam 1.10.89.0）

- 存档从 1.0.48 副本的存档目录复制到 Steam 账号的存档目录（19 个文件，不覆盖），Steam 版能读。首次启动要装 PlayStation PC SDK 运行库（UAC）并编译着色器。
- 发行安装器装上两个变体，读档后私人房间里显示 Karin（agent 截图）；有表情版的截图里在眨眼。只看了私人房间：室外、雨天、过场没看。
- 同时发现有表情版脸上的山姆晒伤层（1.0.48 上就有，不是移植引起的），v35 用链接表修掉，见 [表情](FACE.md#4-阴影与天气)。
- 启动和远程操作的坑见 [排障手册](TROUBLESHOOTING.md#症状定位)。

## 8. 拿不到新版本时：玩家数据收集工具

在拿到 Steam 版之前，为了让报告问题的玩家把必要数据发回来，做了只读的收集工具 `release/collect.ps1`（发行名 `收集游戏数据.bat`，Windows PowerShell 5.1，内嵌 C#）。这次没用上（本地有了 Steam 版），留给以后的版本：

- 拒绝条件：游戏里装着 Karin mod（`KarinMod_backup\state.json` 存在，或流图 Files 里有 `package.99`）。
- 输出 `KarinMod_data_<版本>.zip`（1.0.48 演练约 1.2 GB）：
  - `report.json`（format 2：全部组的指纹；明细组的 span 解压 SHA-1、locator、子组、链接记录）、`groups.tsv`、`types.txt`、`collect.json`；
  - `LocalCacheWinGame\package\`：流图和链接表原样；涉及的 DSAR 包**保留文件头和整张块表**，只带需要的块（重新排偏移），没带的块 `csize = 0`，读到就报错，不会静默读出错数据；非 DSAR 的普通文件只带需要的区间（`.karin_ranges`：魔数 `KRNG`、版本 1、原文件大小、区间表、数据）。
  - 带哪些：mod 的组和它们的子组闭包（整组：核心 + 每个 locator 到同文件下一个 locator / span 起点为止的 stream），外加明细组的对象。
- 我们这边：`sparse_root.py` 把 zip 解成工具根目录（普通文件还原成稀疏文件、补 `.org` 流图、复制 id-daemon 工具、写 `decima.ini`）；`dry_verify.py` 拿重建根目录和完整根目录逐组比读出的数据；`diagcompare.py` 比两份报告（类型、全图指纹、明细组数据 / 子组 / locator / 链接记录、manifest 每处链接补丁在对方版本里指向什么）。
- 构建脚本都能指向别的根目录：`DS2_ROOT`（`graph.py`、`make_mod_ds2.ps1`、`pack.ps1`）、`export_group.ps1 -Tool / -WorkRoot`、`make_links.py --root`。
- 演练（把 1.0.48 当成玩家的版本）：1 分钟出 1196 MB zip（47 个包文件，45 个 DSAR + 2 个普通文件）；`dry_verify` 25862 次读取、1.84 GB 解压数据 0 失败；从重建根目录导出构建用到的 13 个组（1435 个文件）与原导出逐字节相同；完整重建 v34 / v34f，包、流图、链接表与发行的逐字节相同。

## 9. 下次游戏更新

1. 拿到新版文件（本地副本，或玩家的收集 zip → `sparse_root.py`）。
2. `mapgroups.py`（旧根、旧流图、旧链接表、旧报告 zip、新根、输出、两个 manifest）：看组是否都对上、哪些组的数据变了；变了的组用 `corediff.py` 看是哪些字段。
3. 如果只是改号 + 少量字段：`port_release.py` 对两个变体各出一个 `manifest_<版本>.json`；`port_verify.py`、`port_fields.py` 核对；放进发行包的变体目录，安装器会自动选用。
4. 如果 mod 改过的字节也被新版改了（`merge_span` 报冲突），或组的结构变了（对象数、span 长度、链接记录条数），移植不了，要在新版根目录上重新构建（`DS2_ROOT` + 重新导出）。
5. 实机：装上后在同一存档同一场景对照。

旧版原版一直用干净根目录 + 旧版的收集报告（每个 span 的 SHA-1）。
