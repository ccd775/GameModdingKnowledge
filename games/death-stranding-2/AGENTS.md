# Agent 入口（Death Stranding 2 PC）

先读 [README](README.md)，再按当前问题进入对应文档。项目的当前状态在各自的项目目录（`SOP/PROJECT_STATE.md`）里，不在这里；本目录只提供方法、数值快照和已被证伪的假设。

## 接手新任务前

1. **核对版本。** 看 `DS2.exe` 的 FileVersion 和原版 `streaming_graph.core` 的 SHA-256。本目录的快照是 1.0.48.0、`2ECAB7038B9B4AF650B0DB9E817389B63DD79B056DA02A13AA36945FF88DF380`。版本变了，下面这些都要重新确认：
   - 组号（50107、50108、50110、50120、50121、67699、67704、31123 …）、对象下标、网格和贴图编号；
   - `make_mod_ds2.ps1` 里各组 `.core.pristine` 的文件名（文件名就是原版 span 的位置）；
   - 链接表里每一条重指的源与目标（`make_links.py`）；
   - Odradek 类型表能否读通流图（`graph.py` 读不出就先换类型表）。

   发行包的安装器会自动做最后一步核对：只要有一个组和 1.0.48.0 不一样，它就拒绝，并且不写任何文件。
2. **准备干净根目录**（`setup_cleanroot.ps1`）。安装 mod 之后，游戏目录里的流图已经改过，导出、导入、打包、分析都要在指向原版的干净根目录里做，见 [技术合同](TECHNICAL_CONTRACTS.md#干净根目录)。
3. **分清本版改什么。** 几何、权重、贴图页、核心补丁、链接表、打包这几类改动的验收口径不同。实机反馈常常同时涉及好几处，要逐项写清哪一项改了什么、用什么证据。
4. **先查是不是状态。** 物理、脏污、湿身、兜帽、淋浴都会随游戏状态切换。用户说“没了”“又出现了”时，先问清楚在哪个存档、哪个场景、做了什么，再回到上一次正常的场景对照。

## 硬性规矩（本项目已付过学费）

- **干净根目录里的包文件是游戏文件的硬链接，绝不原地写。** 写游戏文件一律“写临时文件 → 删原文件 → 改名”。原地写会同时改坏干净根目录里的原版。
- **每次打包前从 `streaming_graph.core.org` 恢复流图。** `Decima_pack_ds2` 原地改写干净根目录里的 `streaming_graph.core`（`pack.ps1` 已经这么做，打完再恢复）。
- **校验已装的 mod 要传 `graph_path` 和包文件的 `overrides`。** 直接 `Graph(<游戏目录>)` 读到的是干净根目录里的原版。
- **隐藏用塌缩，不用隐藏标志。** `IsHideAndDisableDefault` 会被游戏按装备状态覆盖，v2 设了头发部件的隐藏标志，头发照样在。塌缩保留原版顶点数和索引数，所有顶点放到同一点、全权重挂在一根骨上。
- **整个换掉覆盖模型会崩。** v4 把头发覆盖模型 `50108:23.ModelResource` 改指别的模型，读档就闪退（0xc0000005）。只改部件的 `MeshResource` 是安全的。
- **链接只能指到本组或它的子组**（`Ref`）；`StreamingRef` 记录里写的是组号，可以指任意组。记录长度不够时（比如 2 字节的本地记录装不下 ≥ 8192 的下标），改指它上一级对象的字段。
- **玩家组 31123 的核心不进包。** 往 31123 里写网格必须补齐到原计数（stream-only），`make_mod_ds2.ps1` 会核对工具写出的核心和原版逐字节相同，不同就中止。v25 把 31123 的核心打进包，包变成 295 MB，而且没起作用。
- **外套 / 身体 / 靴子材质的 UV1 不是贴图 UV。** 那是贴花 / 细节层的坐标，原版大多是一个常量。把 Karin 的页面 UV 复制进去，尾巴上就会印出按扣圆点或山姆外套背后的标志笔画。非图集的 UV 组写原版中位数。
- **眨眼只闭一半时先看游戏给的强度。** `BlinkSettingResource` 让普通眨眼只走到控制值约 0.52，按 1.0 拟合的眼睑只闭三分之一到一半。按 0.55 拟合，代价是睡觉闭眼和向下看时会过闭。
- **一个模型改两个版本时，两个链接表一起改。** 有表情版的链接表多了脸皮 LOD0/1 → 186、部件 43 保持原版；`make_links.py` 用版本号后缀 `f` 区分。
- **不要声称实机通过。** 离线闸门全绿、等价性逐字节一致，都只是 `offline-accepted`；实机结论要写清是谁、在哪个场景确认的。
- **桌面和按键。** 远程实机时游戏不在前台绝不发键；每次代理调用都会抢焦点，让游戏弹出系统菜单，先点回焦点。用户通常自己进游戏测，默认构建并安装后交给用户，启动游戏前先问。

## 报告口径

每条结论要归入以下一类：`invariant`、`build-sensitive`、`case-derived`、`hypothesis`、`rejected`。

- 历史失败不删除。新证据只用来收窄旧结论的适用范围，并写明 supersedes 关系。
- 实机结果要绑定到所测包的哈希。
- 要写明是谁测的：agent 自测和用户确认是两个证据等级。
