# Agent 入口（仁王3 Nioh 3）

先读 [README](README.md)，再按当前问题进入对应文档。项目当前状态写在独立工程的 `PROJECT_STATE.md` 里，不在这里。
本目录只提供方法、合同和已被否定的假设。

## 接手一个新任务前

1. **核对游戏版本**：`Nioh3.exe` 的文件版本（本目录快照是 2.0.0.2）。
   - 版本变了，先用 `ktdata.py extract` 取出要替换的原版资源，和便携包的 `configs/vanilla.json`（v2.0.0.2 的 sha256）对一遍。安装器 `karin_install.py install` 开始时也做这一步，不符就停下。
   - 对不上就重新提取模板模型，回到 [构建流水线](BUILD_PIPELINE.md) §1 重新定位。
2. **核对资源表的状态**：`<游戏目录>/package/` 下有没有 `root.rdb.original`、`root.rdx.original`、`n3inject.json`、`0x4b415249.fdata`。
   - 有就说明装过；先 `n3inject.py verify` 看当前装的是哪一版，再对照发行包的 `package.json`。
   - 别的工具（例如 yumia_fdata_tools）也改写 `root.rdb`。两者不能同时装，后装的会盖掉先装的。
3. **确认存档能用、角色穿的是替换目标**：忍者流派要穿 Tirador: Coraza（`0x5548953f`），武士流派要穿 Tropa irregular: Coraza（`0xed9b4309`）。
   Karin 挂在上衣上，换了上衣就是一个缺头缺身体的角色。首次进游戏前备份存档。
4. **测试机是共用的**：用户可能正在上面玩，别的会话也可能占着桌面。
   - 发桌面动作之前先读桌面锁，确认游戏窗口在前台。
   - **用户在玩的时候什么桌面动作都不发，截图也不行。**
5. **一个构建只改一类东西**（模型、贴图、物理结构、物理参数、碰撞、表情），新构建放新目录，不覆盖已有构建和已确认的发行包。

## 硬性规矩（本项目已付过学费）

- **不写、不装 DLL 加载器**，用资源表注入（`n3inject.py`）。注入器只写 `root.rdb`、`root.rdx`、首次备份和新容器。
- **不删、不挪原版子网格**。隐藏用三角形塌缩；被替换模型里每个材质至少保留它原有的子网格，每个 type-5 布料条目保留它的类型 1 网格。
  把原版子网格改到别的材质，会留下「被计数却没有子网格」的材质。计数调高去凑，载入角色就崩溃（build12–18）。
- **每个材质的子网格必须连续**。计数记录按子网格下标顺序分段。新网格插在最后一个原版材质 0 子网格之后，后面的下标顺延。
  追加到末尾会让新网格落进别的材质的段里，就不画了（build20 忍者裙子缺了右半边）。
- **计数资源和物理注册表跟着模型一起重写**（`n3_registry.py`），数字必须等于构建出来的模型的实际值，多了崩溃，少了不画。
- **FM1G 的统计字段随改动同步**：矩阵数、调色板条目、各类缓冲数、MESH_LOD 组数、type-4 统计、LLOC 计数。
  type-4 统计留 0 会在主菜单载入角色时崩溃。
- **调色板写存储序号，不写骨号**。骨号 0–24 和存储序号相同，100 以后不同。拿浪人的做法照搬会把权重绑错骨。
- **判断左右手按骨架父子链，不按奇偶**：左手手指是**偶数**骨号。曾把 474 个顶点并到了另一侧前臂，袖口被拉长。
- **改材质要同时改子网格的三个字段**：+12 运行时材质组、+20 shader、+24 material。只改后两个仍然用原来的贴图（build4 紫色网眼袖子）。
- **先看运行时读了哪张贴图再改**：静态 KTID 会被 TextureAlias 的染色变体盖掉。用 ETW 追踪和 `find_variant.py` 找当前染色（build2/3、build8 第一版都改错了表）。
- **换装形态键不能动到衣服开口那一圈**：袜口那圈收进去，袜子上方的裸露皮肤就成了往里收的锥形（build22）。按高度遮罩，开口那圈权重为 0。
- **物理是否在跑，看关卡里静止时耳朵和裙摆有没有下垂**，不要看主菜单，也不要看跑动截图。
- **远端上传路径写正斜杠**（`<远端工作目录>/build24/…`）。反斜杠加 `$` 会被 shell 转义成字面量，曾把文件写进了 `build2$(basename …` 这样的目录。
- **全分辨率 PNG 会卡住远程隧道**，截图先在远端转成 JPEG 再拉回。
- **不把离线检查、主菜单截图说成实机通过。** 用户在关卡里实际玩过、给了反馈才算 `runtime-confirmed`。
- **modding 工作的审计默认降档**：用户没要求时不派审计，自查后交付，报告里写明。

## 报告口径

结论归入 `invariant` / `build-sensitive` / `case-derived` / `hypothesis` / `rejected` 之一。
历史失败不删；后来的证据只用来收窄旧结论的适用范围，并写明哪条取代了哪条。例如：

- 「双马尾跑动时后飘，物理在跑」被证伪：跑动截图里的是动画，物理当时只在标题画面模拟；
- 「部件不显示是因为 type-4 id 太大」被证伪：真正的原因是材质计数。
