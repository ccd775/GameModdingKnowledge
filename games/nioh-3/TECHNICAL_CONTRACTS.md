# 技术合同（v2.0.0.2）

标注：`[I]` = 引擎 / 格式不变量（在本作的样本里成立）；`[B]` = 随版本变化；`[C]` = 本案例数值。
物理相关的格式在 [物理](PHYSICS.md)，面部在 [表情](FACE.md)，贴图在 [材质与贴图](MATERIALS_AND_TEXTURES.md) 和 [G1T 格式](G1T_FORMAT.md)。

## 1. 加载：资源表注入

- `[I]` 游戏数据在 `<游戏目录>/package/`：`root.rdb`（记录）、`root.rdx`（容器序号 → 容器哈希）、`0x<哈希>.fdata` 容器，
  另有 `data/xx/0x<哈希>.file` 形式的外部资源。格式和浪人崛起同构（`games/rise-of-the-ronin/TECHNICAL_CONTRACTS.md` §2）。
- `[I]` 覆盖方法（`n3inject.py`，与 eArmada8 的 yumia_fdata_tools 同一方案）：
  1. 首次使用时把 `root.rdb` / `root.rdx` 备份成 `.original`；之后每次安装都从备份重新生成。
  2. 所有覆盖文件 `0x<哈希>.<扩展名>` 不压缩地写进一个新容器：头 `PDRK0000` + u32 0x10 + u32 容器总长；
     每个条目 `IDRK0000` + 3×u64（条目大小、存储大小、解压后大小，后两者相等）+ 4×u32（条目类型、名称哈希、类型哈希、0）+ 原版 fdata 条目的参数块 + 载荷，16 字节对齐。
  3. `root.rdx` 末尾追加一个槽 `(u16 序号, i16 −1, u32 容器哈希)`。`[B]` v2.0.0.2 原有槽号最大 157，新槽是 158；`[C]` 容器哈希 `0x4b415249`（"KARI"）。
  4. `root.rdb` 里被覆盖的记录整条重建：`IDRK0000`、记录大小 `0x3D + 参数块长`、尾部大小 `0xD`、文件大小；原记录的条目类型、名称哈希、类型哈希，flags `0x20000`；
     原记录的参数块；13 字节尾部 `u16 0x401（在 fdata 里）, u32 偏移, u32 条目长, u16 容器槽, u8 0`，再补 0 到 4 字节对齐。其余记录逐字节照抄（4 字节对齐）。
- `[I]` 被覆盖的资源必须原本在 fdata 容器里；外部 `.file` 资源这个方案不支持。新文件比原版大没关系。
- `[I]` 注入器把自己写出的 `root.rdb` / `root.rdx` 的 sha256 记在 `n3inject.json`。游戏更新或校验文件后，两张表既不是注入器写的、也不是备份，
  说明备份过期了：安装改为备份游戏当前的表，卸载也不再把过期备份写回去。
- `[I]` 卸载 = 备份放回 + 删除新容器。校验 = 通过 `root.rdb` 把每个覆盖解出来，和 mod 文件逐字节比较。
- 别的改 `root.rdb` 的 mod 会和它冲突：每次安装都从 `.original` 重新生成，会盖掉别的 mod 的记录。
- 本项目**不用 DLL 代理加载器**。改资源表就够了，也不改 exe。

## 2. 资源、KTID 与对象库

- `[I]` 类型哈希：G1M `0x563BDEF1`；G1T `0xAFBEC60C` / `0xAD57EBBA`、KTID `0x8E39AA37` / `0xBE144B78`（`ktdata.py` 沿用浪人的两种）；kidsobjdb `0x20A6A0BB`；
  物理注册表 `0xB340861A`；每材质计数 `0x56EFE45C`。
  `g1fpose` / `g1frani`（面部）见 [表情](FACE.md)。
- `[B]` 一部分 `0x563BDEF1` 记录（坐骑、道具，不是装备）在 `root.rdb` 里记的是压缩后的大小，`ktdata.py` 会报 "metadata differs"；改用 fdata 条目头里的大小就能解出（`extract_many.py`）。
- `[I]` 模型 → 资源的关系在 CharacterEditor 对象库（`0xB290631C`）里：第一个值等于模型哈希的条目，它的属性引用别的条目。
  - `[I]` 属性 `0x7F0DE9A3` → 物理注册表；属性 `0x3BBFD9A5` → 每材质计数；贴图表（KTID）也从这里引出。`model_refs.py <package> <模型哈希>` 列出全部。
  - `[C]` 忍者上衣 `0x5548953f`：注册表 `0x5583ad7d`，计数 `0x5c3826bd`；武士上衣 `0xed9b4309`：注册表 `0xedd65b47`，计数 `0xf48ad487`。
- `[I]` KTID 载荷 = `(槽号, 对象哈希)` 对；对象的第一个值是 G1T 哈希。`ktid_repoint.py` 按 G1T 哈希把槽改指向别的对象（目标贴图必须已经是某个对象的第一个值），
  `ktid_setref.py` 直接写 `(槽号, 对象)`。运行时还要经过 TextureAlias（[材质与贴图](MATERIALS_AND_TEXTURES.md) §2）。

## 3. G1M

块：`FM1G`（计数）、`SM1G`（骨架）、`MM1G`（逆绑定矩阵）、`GM1G`（几何，节：VERTEX_BUFFERS、VERTEX_ATTRIBUTES、JOINT_PALETTES、INDEX_BUFFER、SUBMESH、MESH_LOD 等）、
`LLOC`（碰撞体）、`ONUN`（NUNO 物理）。字段布局与 gust_stuff 的 `parseG1MS` / `parseG1MG` 一致，便携包的 `g1m_tool.py` 独立实现了读取。

### 3.1 FM1G 计数（随改动同步）

| 偏移 | 内容 |
| --- | --- |
| +12 | SM1G 组数（1 + type-4 条目数） |
| +16 | 关节数 |
| +24 | MM1G 矩阵数 |
| +52 / +60 | 顶点缓冲数 |
| +56 | 属性集数 |
| +64 | 调色板数 |
| +68 | 调色板条目总数 |
| +72 | 索引缓冲数 |
| +76 / +80 / +92 | 子网格数 |
| +88 | MESH_LOD 组数（c1 + c2） |
| +96 / +100 | LLOC 组数 / 碰撞体总数 |
| +136 | 骨号空间 |
| +276 … +332 | type-4 统计（[物理](PHYSICS.md) §1） |

`[I]` type-4 统计留 0 时，主菜单载入角色就崩溃（0xC0000005）。

### 3.2 子网格与 MESH_LOD

- `[I]` SUBMESH 记录的 +12 是**运行时材质组**，+20 是 shader，+24 是 material。改材质三个都要改；只改后两个，游戏仍然用原来那组贴图。
- `[I]` MESH_LOD 给每个子网格一个网格组：组名哈希（`[C]` `@EE29F247` 主体常显；`@B96555CF` 腰带；`@A0AB8A96` 布料）、类型（0 普通，1 = type-5 布料驱动，
  2 = type-4 骨链驱动）、NUN id（类型 1 为 `0x4e20 + k`，类型 2 为 `0x2710 + k`，k 是条目在 ONUN 里的序号）。
  - 拿来放 Karin 的子网格要抄主体子网格的组。组名决定什么时候显示：忍者上衣子网格 1 是戴手甲时隐藏的空手，改了组名也照样不显示。
- `[I]` 每材质计数按**子网格下标顺序**分段（[§5](#5-每材质计数与物理注册表)）：每个材质的子网格必须连续。
- `[I]` 原版 430 个模型里有 24 个子网格不按材质排序（含带 type-4 物理的头发 `0xd5d385f9`），所以只要每个材质连续，不要求全局按材质排序。

### 3.3 顶点与调色板

- `[I]` 蒙皮顶点：8 个 f16 权重，降序，和为 1；法线 w = 0；**存储的切线沿 −dP/dv，w·cross(N, T) 沿 −dP/du**。
- `[I]` **调色板存的是 SM1G 的存储序号，不是骨号**。原生绑定按存储序号核对，误差 0.0036。骨号 0–24 和存储序号相同，100 以后不同。浪人崛起正好相反。
- `[I]` u8 骨骼索引 = 调色板下标 × 3，每个调色板最多 85 项。超过 85 时改用 u16 BLENDINDICES（数据类型 7，仍是 ×3 编码），属性集里后面的偏移顺延，步长每组 +4。
  - 原版女性头的脸皮子网格用 124–128 项；上衣着色器也认，主体子网格 107 项、步长 56 → 64 实机正常；上限按 128 处理。
- `[I]` 每个调色板条目都要有 MM1G 逆绑定。缺的就按原生规则追加，并把 FM1G +24 加上。
- `[C]` 忍者上衣 `0x5548953f`：sub0 VB0 8 权重步长 56，材质 0（2048 BC7 颜色）→ Karin 主体；sub1 VB1 4 权重步长 48，材质 1（空手）；
  sub2 VB2 布料（步长 132，NUNO 围巾，MESH_LOD 类型 1），材质 2；sub3 VB3 8 权重步长 56，材质 2。
- `[C]` 武士上衣 `0xed9b4309`：sub0 / sub1 布料（步长 132，类型 1），材质 0；sub2 8 权重步长 56，材质 0 → Karin 主体；sub3 4 权重步长 40，材质 1（腰带）。

### 3.4 写入规则（本项目最终采用的布局，build21 起）

1. Karin 的主体写进模板的主体子网格（rest），调色板按实际用到的骨重建。
2. 其余部分（手臂、裙子 / 脸、每个 type-4 条目一个网格）作为新子网格**插在最后一个原版材质 0 子网格之后**；
   顶点缓冲 / 属性集 / 调色板 / 索引缓冲也插在材质 0 用到的最后一个之后，后面的原版下标顺延。
3. 每个新子网格有自己的顶点缓冲、属性集（主体的布局）、调色板、索引缓冲和 SUBMESH 记录（抄主体：材质组 0、shader 0、material 0），以及一个 MESH_LOD 组。
4. 原版的其余子网格全部保留，三角形塌缩。
5. FM1G 计数、GM1G 包围盒随改动更新；计数资源和注册表按构建结果重写。

## 4. 骨架

- `[I]` 单位 cm，Y 向上，+Z 向前，**+X 是角色左侧**；手臂约 45° 的 A 字姿势；头骨 y ≈ 164.5。
- `[B]` 骨号：胯 2、大腿 3/4、膝 5/6、踝 7/8、脊 9、胸 10、颈 11、头 12、锁骨 13/14、上臂 15/16、肘 17/18、腕 19/20、趾 23/24。
  左手手指：拇 100-108-118、食 102-110-120、中 104-112-122、无名 114-124-128、小 116-126-130；右手 +1，**左手是偶数**。
- `[I]` 胯骨 2 的世界轴：局部 x = 上，y = 前，z = 角色左侧。在骨空间里放碰撞体时要换算（[物理](PHYSICS.md) §4）。
- `[I]` 原版身体的四肢绑在扭转 / 辅助骨上，不直接用 3–6、15–18。贴身的衣物和皮肤从原版基础身体按最近点迁移权重最稳。
- `[I]` 每个玩家模型都带完整的面部骨（骨号 400–737），属于基础身体的骨架，全角色共享；模型自己的私有骨号可以互相重叠
  （忍者上衣 1000–1032，头发 953–1300）。新增的物理关节接在模型已有的骨号空间之后。

## 5. 每材质计数与物理注册表

- `[I]` 每材质计数（类型 `0x56EFE45C`）：每个材质一条 32 字节记录 `(哈希, 0, 子网格数, 0, 0, 顶点缓冲数, 0, 0)`；别的模型的 +12 / +24 也有数。
  - 远端统计 13259 个原版计数资源，**没有一条记录全为 0**。
  - 计数少于实际：超出的类型 2 网格不画（build12–15）。
  - 计数多于实际：载入角色就崩溃，`Nioh3.exe` 2.0.0.2 RVA `0x195297`（`movsxd r8,[rdi+rbx*4+0x14]`，`rdi` 是从按槽位下标的指针数组里取出的空指针；build16–18）。
  - 结论：计数必须等于实际值；材质不能没有子网格。
- `[I]` 物理注册表（类型 `0xB340861A`）：`u32 组数, 材质数, type-5 数, type-4 数`；每组 `(哈希, n, n 个材质号)`；type-5 条目 `(x, id)`；
  type-4 条目 `(x, id)`，按 ONUN 顺序，x = 同一材质的 type-4 条目里的序号。原版最多 60 个条目，id 最大 200（2101 个样本）。
  只注册不会多画任何东西（build15）；注册了但网格是类型 0，完全不模拟（build19）。
- `[C]` 忍者计数资源 `0x5c3826bd` 与另一件上衣 `0x1af713a6` 共用（布局相同，自己的注册表 `0x1b322be4`），后者的材质 0 会被多计。未观察到问题，也没有测过那件上衣。

## 6. 隐藏原版部件

- `[I]` 三角形塌缩成同一个索引（`g1m_tool.py hide`），文件长度不变，G1H 容器（多个内嵌 G1M）也照样有效。
- `[C]` 隐藏的 13 个模型：头 `0xdb009737`、臂 `0xf9a39659`、腰腿 `0xfed6b90c`、靴 `0x11ec2bff` `0x8a713ad2`（含武士胫甲）、裹胸 `0xa0b0dd1d`、
  基础身体 `0x4ba258df`、女性捏脸头 `0xb24cac84`、发型 `0x7c857e61` `0xd5d385f9`、武士袴 `0x8d717eb8`、武士手甲 `0x805e4050`、额饰（武士头盔 Kusanagi）`0x6a0d18db`。
  都是测试存档身上的装备，加上主角的基础身体、捏脸头和发型。
- `[I]` 女性捏脸头 `0xb24cac84` 是 `_H1G` 容器：9 组 × 约 26 个只有 GM1G 的小模型是捏脸滑块的顶点形变，后面才是主 G1M（38 个子网格：0–8 脸皮、9–14 眼球、
  15–34 睫毛 / 眼部变体、35–37 牙）。捏脸只作用在这个头上，不影响 Karin。
- 发行包不带原版模型的副本：安装器从玩家自己的游戏数据提取这 13 个模型，现场塌缩（`collapse.txt`）。远端实测和构建时塌缩的结果逐字节相同。
- 被隐藏的模型任何角色用到都会看不见，包括可能用到它们的 NPC（未测）。

## 7. 崩溃诊断

- 载入角色崩溃时，先看是不是计数（§5）或 FM1G 统计（§3.1）。两种都发生在载入角色的那一刻，不是在游戏中随机发生。
- `Nioh3.exe` 的 `.text` 在磁盘上是加密的；要看崩溃点附近的指令，只能从运行中的进程读。build16–18 的结论就是这样得到的（读到的是空指针，与「计数多出空槽」吻合）。
