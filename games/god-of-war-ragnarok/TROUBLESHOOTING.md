# 排障手册

## 症状定位

| 症状 | 先查 | 本案出现过的原因 |
| --- | --- | --- |
| 卡在开场 logo，进程 CPU 增量接近 0 | 有没有定义超过原容量；有没有哪个网格组全部被清空 | 整个模型写进一个定义（超容量）；裤子组全部清零；隐藏时只留 1 个顶点、索引数为 0 |
| 启动后进程消失（崩溃） | 补丁 lodpack 的目录布局 | 照 root.lodpack 写成一个缓冲区一组 |
| 游戏里角色毫无变化 | 改的是不是游戏真正加载的 wad；boot-options 有没有登记；哈希有没有加 1，wad 头部清单是否同步 | 第一版芙蕾雅改的是没人引用的 `r_freya00.wad` |
| 某个网格组整块变形，跟着错误的骨骼动 | 骨骼索引是否按分量组合编码 | 芙蕾雅头颈组 (9,2,4)+(10,2,2) 应为 8 个 u16，被写成了 11 bit 打包 |
| 裙子和尾巴整体翻到背后 | 是否绑到了不带蒙皮的控制骨 | 芙蕾雅的骨盆角色选了 FK 控制骨 38，应为 14 |
| 角色周围有乱飞的三角形，或一大片乱掉的深色面片 | 隐藏定义指向的零块在哪里 | 零块放在 wad 内 gpu 条目（哈希 0）里，那块区域其实属于别的网格，引擎画出了它的真实三角形 |
| 走路屈膝时膝盖皮肤穿出过膝袜 | 源模型的 `kisekae_*` 形态键是否已烘焙；袜子所在槽位的精度 | 拟合脚本清掉了形态键；袜子在容量小的脚部组，只有 40%–80% 精度，皮肤和袜子的影响骨数也不同（7 对 4） |
| 模型像从里往外看 | 三角形绕序 | Blender 数据是逆时针，GoWR 以顺时针为正面 |
| 左右肢体互换或镜像 | 坐标映射 | Blender (x, y, z) → 游戏 (−x, z, y)，角色左侧在游戏 −X |
| 贴图解码出来是乱码 | 条目前缀第二个 u32（数据起始偏移） | 按固定偏移读，误把参照 mod 的正常贴图判成坏的 |
| 远处或拉远镜头后又出现原角色 | 各 LOD 是否都写入了 | 本案奎托斯 LOD0–4、芙蕾雅全部 LOD 都写了，远景切换未在实机确认 |
| 俯视时头顶、耳尖、肩上出现黑斑（奎托斯版） | 皮肤材质的叠加层 | 未处理。只出现在朝上的表面，猜测是游戏给奎托斯皮肤叠的灰尘层（`hypothesis`） |
| 不确定看到的东西来自哪个材质 | 出一个诊断贴图包 | 见 [验证与发布](VALIDATION_AND_RELEASE.md#离线闸门) |

## 卡死与崩溃的二分记录

2026-10-02 在奎托斯上逐个测试最小构建（自动启动，按 CPU 增量判断卡死）。这串测试定下了两条硬限制和隐藏写法：

| 测试 | 构建 | 结果 |
| --- | --- | --- |
| B | 整个 Karin（33612 顶点）写进头部定义 1138，缓冲区按新大小重写 | 卡 logo |
| C | 同上，缓冲区补齐到原大小，但顶点数仍超过原容量（23081） | 卡 logo |
| D1 | 参照 mod 自己的缓冲区，用「一个缓冲区一组」的布局重新打包 | 崩溃 |
| D2 | 参照 mod 原来的 lodpack 改名后登记（排除包名和登记方式的影响） | 正常 |
| D3 | C 的数据改用单组布局 | 崩溃 |
| E | Karin 拆成两块，原地写进 1138 和 1140，都在容量内 | 正常 |
| F | 完整构建，其余定义全部清零 | 卡 logo |
| G | 只清零 LOD0 的兄弟定义 | 正常 |
| H | 清零所有流缓冲区里的定义，保留 wad 内（哈希 0）的定义 | 卡 logo |
| I | 清零盔甲和裤子，保留身体各 LOD | 崩溃 |
| J1 | 只清零裤子组（组 267）的全部定义 | 卡 logo |
| J2 | 清空各 LOD 的定义，但每组 LOD0 留一个非空网格 | 正常 |
| K | 隐藏写成顶点数 1、索引数 0 | 卡 logo |
| L | 隐藏写成退化三角形，零块在发布的缓冲区里 | 正常 |
| M | L 加上自己的贴图包 | 正常，后续实机测试的基础 |

- B、C → 硬限制 1（容量）；J1 对 J2 → 硬限制 2（每组至少一个非空网格）；K 对 L → 隐藏必须画三角形。
- D1 对 D2 → 补丁 lodpack 用单组布局。单组写法重写参照 mod 的缓冲区，结果与参照 mod 的 lodpack 逐字节相同。
- 结果都绑定在当时的测试构建上，二分没有覆盖所有组合。例如 I 崩溃的具体原因没有单独确认，已由「每组留一个非空网格」的规则覆盖。

## 被否决的做法

- **改 `r_freya00.wad` 替换芙蕾雅（`rejected`，用户实机反馈）。** 资源依赖表里没有任何资源引用它。改为 `r_freyavalkyrie00.wad`。
- **整个模型放进一个定义（`rejected`）。** 超容量就卡死，见测试 B / C。改为按容量拆进同组的几个定义。
- **补丁 lodpack 一个缓冲区一组（`rejected`）。** 见测试 D1。
- **清零计数来隐藏网格（`rejected`）。** 见测试 J1 / K。
- **零块放进 wad 内的 gpu 条目（`rejected`，芙蕾雅实机）。** 出现乱飞的三角形。改为放在随补丁包发布的缓冲区里，并检查不与计划槽位重叠。
- **所有 (9,2,4) 骨骼分量都按 11 bit 打包（`rejected`，芙蕾雅实机）。** 要按骨骼和权重分量的组合判断。
- **按位置挑骨骼，不看蒙皮（`rejected`，芙蕾雅实机）。** 同一关节上叠着不带蒙皮的控制骨。
- **回读时只检查骨骼索引范围（`rejected`）。** 骨骼格式写错也能通过。改为逐顶点比对骨骼集合和权重。
- **在 Blender 里用最近距离测膝盖穿模（`rejected`）。** 弯曲后会把关节另一侧折过来的面当成最近面，结果不稳定。改为 `knee_sim.py`：在绑定姿势下先定对应关系。
- **Steam 离线时用「验证文件完整性」恢复原版（`rejected`）。** 验证失败，还删掉了 `exec/boot-options.json`。改为自己备份原版。

## 元教训

- **先找真正的使用者。** 在依赖表里确认 wad 被谁引用，比对着文件名猜可靠。
- **卡死时用最小构建二分。** 每个测试只改一类东西，配一个便宜的卡死判据（CPU 增量）。规则都来自二分结果，不是从格式推出来的。
- **验证要检查真正关心的性质。** 骨骼格式这类错误只有逐顶点比对才能抓到。
- **多个游戏重复出现的问题，修在源头。** 膝盖穿模在多个项目里出现过，这次直接修正共享源模型，并保留 `.orig`。
