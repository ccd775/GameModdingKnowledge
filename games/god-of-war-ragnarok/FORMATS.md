# 格式

下面的布局都在 build `18979360` 上读写验证过。wad 的条目偏移解析移植自 kainotoa 的 GOWTool（`gowr-pc` 分支，commit `ef484028`，`src/Wad.cpp` 与 `src/Formats.cpp`），其余字段是本项目核实或补充的。偏移和数值都是 `build-sensitive`。

## 文件与加载

| 位置（游戏目录下） | 内容 |
| --- | --- |
| `exec/wad/pc_le/r_<角色>.wad` | 角色资源包：网格定义、网格组、骨架、贴图定义和低分辨率贴图 |
| `exec/wad/pc_le/root.lodpack` + `.toc` | 原版流缓冲区（网格顶点和索引） |
| `exec/wad/pc_le/root.texpack` + `.toc`，以及其他 `*.texpack` | 原版全分辨率贴图 |
| `exec/wad/pc_le/resource_dependency_graph.json` | 资源依赖表（LZ4 帧压缩的 JSON） |
| `exec/boot-options.json` | 启动配置，补丁包在这里登记 |
| `exec/patch/` | mod 的补丁包放这里 |
| `libSceAgcTextureTool.dll`（游戏根目录） | 游戏自带的 PS5 贴图 tiling 库 |

- **补丁包登记。** 在 `boot-options.json` 的 `patch-texpacks` 和 `patch-lodpacks` 数组里写 `"../../patch/<包名>"`（不带扩展名）。原版两个数组都是空的。
  - 同时装两个 mod 时，两个包名都写进去；
  - 补丁包按哈希覆盖原版数据，不需要解压 `root.texpack.toc`。
- **wad 直接替换。** mod 的 wad 覆盖 `exec/wad/pc_le/` 里的同名文件。原版 wad 是 LZ4 帧压缩的，解压后的未压缩 wad 游戏也能直接读。

## 资源依赖表

`resource_dependency_graph.json` 是 LZ4 帧压缩（魔数 `04 22 4D 18`）的 JSON，记录每个资源依赖哪些资源。换角色前先在里面找 `R_<wad 名>` 被谁依赖：

- `R_FreyaValkyrie00`：有 10 个关卡和同伴资源依赖它，游戏里的芙蕾雅用的就是它；
- `R_Freya00`：没有任何资源依赖它，改了也看不到。

文件名不能说明一切：`r_freya00.wad` 里同样有完整的芙蕾雅网格和贴图。

## WAD（WTOC v2）

- **头部：** 解压后开头是 `WTOC`，`+4` 为版本（2），`+8` 为条目数。条目表从 `0x40` 开始，每条 `0x90` 字节，数据区紧跟在条目表后面。
- **条目字段：**
  - `+0` u16 group、`+2` u16 type、`+4` u32 size；
  - `+0x18..0x50`：名字；
  - `+0x6F` bitset、`+0x72` flush 标志、`+0x78` 偏移。
- **数据偏移**不是直接存的，要按 flush 队列模拟出来（`wad.py`，移植自 GOWTool）。
- **本项目用到的条目**（以奎托斯为例，`<n>` = `heroa00`）：

| 条目 | type | 内容 |
| --- | --- | --- |
| 第 1 条（下标 1） | — | 头部流清单：本 wad 引用的流缓冲区哈希（后跟 u32 大小） |
| `MESH_<n>_0` | 1 | 全部网格定义 |
| `MG_<n>_0` | 153 | 网格组与 LOD 表 |
| `MG_<n>_0_gpu` | — | wad 内的小顶点缓冲区（网格定义里哈希为 0 时指向它） |
| `goProto<n>` | — | 骨架 |
| `TX_<贴图名>_<16 位十六进制哈希>` | 34 | 贴图定义，`+0x78..+0x98` 为 32 字节 T# |
| 同名哈希的 gpu 条目 | 32930（group 29） | 常驻的低分辨率贴图数据 |

## MESH 定义

`MESH_<n>_0` 里 `+0xC` 是定义表的位置，`+0x10` 是定义数。定义表里每项是相对自身位置的 u32 指针。每个定义（相对定义起点）：

| 偏移 | 类型 | 内容 |
| --- | --- | --- |
| `+0x10` | 3×f32 | 包围盒半尺寸（extent） |
| `+0x1C` | 3×f32 | 包围盒中心（origin） |
| `+0x30` | u32 | 索引在流缓冲区里的偏移 |
| `+0x3C` | u32 | 第一个顶点流的偏移 |
| `+0x44` / `+0x48` | u32 | 顶点数 / 三角形数 |
| `+0x5C` | u32 | 索引数 |
| `+0x60` / `+0x64` | u32 | 分量表 / 顶点流偏移表的位置（相对定义起点） |
| `+0x68` | u64 | 流缓冲区哈希；0 表示 wad 内的 `MG_<n>_0_gpu` |
| `+0x80` / `+0x81` | u8 | 顶点流个数 / 索引步长（2 = u16） |
| `+0x84` | u8 | 分量个数 |

- **分量表**每项 8 字节，前 5 字节是 `(类型, 数据格式, 个数, 流内偏移, 流编号)`。数据格式的字节数：0=f32、1=u16、2=u32、3=R10G10B10A2、4=u16、6=unorm16、7=snorm16、8=u8。
- **同一个流缓冲区里通常放着好几个定义**（同一 LOD 的几块网格），按顶点偏移排开。

### 容量（硬限制 1）

引擎按原版布局为每个定义预分配资源。写入的顶点数和索引数不能超过原容量，否则启动时卡在 logo。

- 顶点容量 = （索引偏移 − 第一个顶点流偏移）÷ 顶点步长；多个顶点流时取各流可用空间的最小值。
- 索引容量 = （同缓冲区下一个定义的顶点偏移，或缓冲区末尾 − 索引偏移）÷ 索引步长。
- 原地写入时，缓冲区总大小保持不变。

### 顶点分量

| 类型 | 数据格式 × 个数 | 内容 | 写法 |
| --- | --- | --- | --- |
| 0 | f32×3 | 位置 | 直接写 |
| 1、16 | R10G10B10A2×1 | 法线 | snorm：`round(v×512+511)`，W=0 |
| 2 | R10G10B10A2×1 | 切线 | 同上，W=3 |
| 3、4、5、6 | unorm16×2 / snorm16×2 / f32×2 | UV | snorm 的 UV 要保留原网格的整数 tile 偏移 |
| 9 | 见下表 | 骨骼索引（全局骨骼编号） | 见下表 |
| 10 | 见下表 | 权重 | 见下表 |
| 14 | 不定 | 未知的逐顶点数据 | 照抄原网格里出现最多的原始值 |
| 15 | u32×1 | 打包属性 | 照抄原网格里出现最多的值 |

### 骨骼与权重布局（按组合判断）

| 骨骼分量 | 权重分量 | 每顶点影响数 | 骨骼索引 | 权重 |
| --- | --- | --- | --- | --- |
| (9, 2, 4) | (10, 2, 3) | 10 | 10 个 11 bit，从最高位起连续打包进 4 个 u32 | 9 个显式 10 bit unorm（每个 u32 放 3 个），第 10 个隐含为 1 − 和 |
| (9, 2, 4) | (10, 2, 2) | 7 | **8 个 u16**（用 7 个，第 8 个为 0） | 6 个显式，第 7 个隐含 |
| (9, 4, 4) | (10, 3, 1) | 4 | 4 个 u16 | R10G10B10A2 里 3 个 unorm10，第 4 个隐含 |
| (9, 8, 4) | (10, 3, 1) | 4 | 4 个 u8，只能用编号小于 256 的骨骼 | 同上 |

- 第二行是芙蕾雅头颈组（组 36）的布局。按第一行的 11 bit 写进去，整组网格会绑错骨骼。
- 空的骨骼槽：奎托斯填一根固定的骨（1447），芙蕾雅填该顶点的第一根骨。
- 显式权重量化后，要保证和恰好为 1023（隐含槽为空时），否则会多出一个隐含影响。

## MG 网格组

`MG_<n>_0`：`+0x30` 为组数（u16），`+0x44` 起是每组的 u32 偏移。每组：

- `+0`：父组号（u16）。父组为 0 的组始终显示；其余组是可切换的部件（发型、服装、翅膀等）。
- `+0x38` 起：各 LOD 的偏移表。每个 LOD 记录：u32 网格数、`+4` f32 切换距离（米；32767 表示最后一级）、`+10` 起 u16 网格定义下标。

**硬限制 2：** 每个组至少要留一个非空网格，否则加载卡死。隐藏网格的写法见 [构建流程](BUILD_PIPELINE.md#8-隐藏其余网格)。

## 骨架（goProto）

- `+0x10`：骨骼数 n（u16）；`+0x1E + 8i`：第 i 根骨的父骨（i16，-1 为根）。
- 局部矩阵从 `((0x18 + 32n + 15) & ~15) + 0x50` 开始，n 个 4×4 f32；紧接着是 n 个逆绑定矩阵。
- 行向量约定：世界矩阵 = 局部矩阵 × 父骨世界矩阵，平移在第 4 行。
- **坐标：** -Z 朝前，+X 是角色的右侧。Blender 坐标 (x, y, z) 对应游戏 (−x, z, y)。
- **同一关节上可能叠着几根骨。** 芙蕾雅（`goProtofreyaValkyrie00`）的 FK 控制骨（38、141/138、43/44、55/62）不带蒙皮，原版网格绑在它们的子骨上（14、842/836、59/66、82/91）。

## lodpack

`.lodpack.toc` 与 `.lodpack` 开头的目录相同：

- 头部 16 字节：u32 组数、u32 成员数、u64（`1 << 32`）；
- 组表，每组 24 字节：u64 数据偏移、u64 哈希、u32 大小、u32 0；
- 成员表，每个 24 字节：u32 组号、u32 组内偏移、u64 缓冲区哈希、u32 大小、u32 0。

**补丁 lodpack 的写法**（`build_mesh.write_lodpack_single_group`）：

- 只有一个组，紧跟在目录后面；全部缓冲区按哈希升序依次放进这个组；
- 组的哈希写最后一个成员的哈希；
- 用这个写法重写参照 mod 的缓冲区，得到的 lodpack 与参照 mod 逐字节相同。

照 root.lodpack 的写法（一个缓冲区一组、16 字节对齐）写出的补丁包，实机崩溃（二分记录见 [排障手册](TROUBLESHOOTING.md#卡死与崩溃的二分记录)）。

**覆盖规则：** 被替换的缓冲区用「原哈希 + 1」作为新哈希。

- 网格定义 `+0x68` 和 wad 头部流清单里的旧哈希都要改成新哈希；
- 参照 mod 可能已经把某个哈希加过 1，这时原版数据在「哈希 − 1」下（`root_buffer` 的回退逻辑）。

## texpack

- **目录**（`.texpack.toc`，与 `.texpack` 开头相同）：
  - `0x20`：u32 目录大小、u32 条目数、u32 记录表偏移、u32 条目数、u32 6、u32 0；
  - `0x38` 起，每条 24 字节：u64 贴图哈希、u64 第二哈希（从 `root.texpack.toc` 抄）、u64 记录偏移；
  - 每条记录 32 字节：u32 数据偏移 ÷ 16、u32 数据大小、u32 条目大小、u32 0、u32 mip 数、u16 宽、u16 高、i64 −1。
  - 条目按哈希升序排列。
- **条目前缀 16 字节，第二个 u32 是数据起始偏移。** 本项目写的 GNF 条目是 `0x124`，原版裸条目是 `0x20`。起初按固定偏移读，把参照 mod 的正常贴图误判成了坏的。
- **GNF 条目：** `+0x10` 为 `GNF `，`+0x20..0x40` 为 T#，`+0x110` 起是 mip 数和数据大小，数据从 `0x124` 开始，整条按 16 字节补齐。
- **T#：** 格式在第 2 个字的第 20–28 位；宽高、最后一级 mip 也在 T# 里。本项目遇到的块压缩格式：

| 格式号 | 压缩 |
| --- | --- |
| 169、170 | BC1 |
| 173、174 | BC3 |
| 175、176 | BC4 |
| 177、178 | BC5 |
| 181、182 | BC7 |

- **tiling** 调用游戏自带的 `libSceAgcTextureTool.dll`（`agctex.py`）：`initializeWithTSharp`、`tileRegion`、`detileRegion`。区域以 4×4 块为单位；参数顺序是 slice 在前、mip 在后。
- **补丁贴图可以比原版大。** 本项目的漫反射写成 2048 或 4096 的正方形，常量贴图写成 128，都不受原版尺寸限制。格式和通道映射沿用原版 T#，只改尺寸和 mip 数。
