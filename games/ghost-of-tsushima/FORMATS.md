# 格式与交付合同

下面的布局已在 build `23879181` 上逐项读写验证。它们部分来自 Dave349234 的 Blender 工具包，大部分字段是本项目重新核实的。偏移和数值都是 `build-sensitive`。

## 归档与加载

- **原版归档。** `<游戏目录>\cache_pc\psarc\*.psarc` 实际是 **DSAR** 容器：
  - 头部是 `DSAR` 魔数和块数；从 `0x20` 起是 32 字节一条的块表，数据按 LZ4 块压缩；
  - 解压后是一个完整的 PSARC；
  - PSARC 条目按 `md5(文件名)` 排序，要通过哈希定位文件，不能按 manifest 顺序；
  - 本项目用到的原版包：`gapack_misc_h`、`gapack_meshes`、`gapack_bitmaps_h_armor_0`、`gapack_misc_g`。
- **Mod 包。** 一个普通 PSARC，放进 `cache_pc\psarc\`，文件名如 `gapack_misc_h_<Name>.psarc`，同名文件会覆盖原版内容。已验证能用的写法如下：
  - 头部：`PSAR`、v1.4、压缩标记 `zlib`、条目 30 字节、块大小 64 KiB、flags=2（绝对路径 `/…`）；
  - 条目 0 是 manifest，md5 全零，**只有它可以 zlib 压缩**；
  - **所有文件数据按原样存储，不压缩**；
  - 大于等于 64 KiB 的文件起点按 8192 字节对齐，缺口用全零填充块补齐；
  - 条目表写成 `md5 + u32 块号 + 40 位解压大小 + 40 位偏移`，块长度表为 u16（64 KiB 整块记 0）。
- **实机教训：** 数据块用 zlib 压缩的包，游戏过厂商 logo 后黑屏卡死。原版内层 PSARC 和能跑的社区 v1.0 mod 都不压缩数据。
- **替换护甲的 mod 共 83 个文件：**
  - `/hero.xpps`；
  - 5 个槽位材质的全部通道贴图 `/bitmaps/*.sps`，共 43 个；
  - `/meshes/hero_kamakura_armor_all_ranks.xmesh`；
  - 38 个被隐藏网格的 `/meshes/*.xmesh`。

  **每个文件保持原版字节大小**，文件名集合与社区 v1.0 mod 完全一致。
- **冲突：** 多个 mod 改同一批文件时，生效哪一个不确定，只装一个。

## hero.xpps

- **部件记录**（相对记录地址）：
  - `+32` / `+44`：包围盒 min / max，各 3×f32；
  - `+56`：位置 offset，3×f32；
  - `+68`：位置 scale，f32；
  - `+80`：部件哈希，u64；
  - `+152`：索引数；
  - 另外还有顶点数、属性表（格式 ID、步长、数量）和材质。材质地址 `+48` 存的是贴图表的指针和数量，贴图哈希在 `贴图表 + 32 × i`；这些指针都相对数据区起点（包头 `+40` 给出的偏移）。
- **位置量化：** `pos_cm = snorm16 / 32767 × scale + offset`。写入部件时，按新网格的包围盒重设 offset 和 scale。**包围盒字段保持原版**：第一版曾改写它，后来为了减少变量改回原版，能跑的 v1.0 也是这样。
- **隐藏部件：** offset 设为 0，scale 设为 f32 字节 `00 00 08 35`（约 5.1e-7），同时把 xmesh 里该记录的区域清零。
- **布料模拟开关：** 字节 `15 10 a9 12` 改成 `15 10 a8 12`，本 build 正好出现 5 次，对应被用作槽位的 5 个摆动部件，与 v1.0 相同。替换前先断言出现次数就是 5。
- **`0x98..0xA8`**：16 字节包标识。v1.0 用的是非原版值，也能正常加载；游戏不把它当作内容哈希校验。本项目用「清零后整包 md5」生成新值。
- **骨架：**
  - 655 根骨骼，每根 48 字节局部变换：浮点 0–3 为四元数 xyzw，4–6 为位置，8–10 为缩放；单位 cm，x 前、y 左、z 上；
  - 另外在偏移 `239504`（`0x3A790`）存了一份绑定世界矩阵；
  - 官方女主角骨架 `heroine.xpps` 的肩、肘、腕、髋、膝、踝位置与 Jin **完全相同**，没有「女性骨架」可以换。

## xmesh（SMBS）

- **头部：** `SMBS` 魔数；`0x18` 为缓冲起点，`0x20` 为缓冲大小，`0x28` 为记录数；记录从 `0x2C` 开始。
- **每条记录：** `u64 部件哈希`、`u32 索引偏移`、`u16 LOD`、`u8 流数`，后跟 `u32 × 流数` 个流偏移。
  - 记录按索引偏移排序。
  - 流偏移**不一定升序**（原版 `hero_head` 就不是），检查边界时要用最小值和最大值。
  - LOD0 的判据是 `(lod & 0xff) == 0`。
- **槽位部件的属性流**（格式 ID 已核实）：

| 格式 ID | 内容 |
| --- | --- |
| `3252492` | 位置 snorm16×3（与 `2107138` 的 f16 副切线符号交错，共 8 字节） |
| `3252233` | 10:10:10:2，按 `(v+1)/2` 偏置；第一条是法线，第二条是切线 |
| `2205445` | UV f16×2，原点在左上（与 glTF 相同） |
| `11642124` | 骨骼 int16×4，**全局骨骼索引**，-1 表示未用 |
| `11640842` | u8×4：字节 0–2 是骨骼 1..3 的权重，骨骼 0 的权重隐含为 `255 − 和` |

- **三角形：** u16 索引，逆时针为正面。
- **写入规则：** 顶点数和索引数保持原版。多余的索引填退化三角形，多余的顶点可以不用。写入的部件必须全部是上表这套属性格式。

## 贴图（SPS / XTBS）与 texmeshman

- **SPS 布局：**
  - `XTBS` 魔数，`+24` 为数据偏移，`+32` 为名字长度；
  - 名字后再跳 20 字节，依次是 `u32 格式`、`u16 宽`、`u16 高`、`u16 深度`、`u16 mip 数`；
  - 之后是完整的 BC mip 链。
- **按格式 ID 分类的压缩方式：**
  - 漫反射（d）：BC1（`251725312`）或 BC3（`251725824`）；
  - 法线（n）：BC5；
  - 其余通道：BC4。
- **写入：** 保留原版头部，只替换 mip 链。数据长度必须与原版相同，也就是尺寸、mip 数和格式都不变。
- **贴图名查找：** 材质记录里只有贴图哈希，要用 `/game.sprig.texmeshman`（`NAMS` 表）把哈希映射成名字。名字形如 `<材质名>.msac.<通道>.<…>`，通道包括 d、n、s、g、ao、m 等。
- **编码：** 漫反射用 DirectXTex `texconv` 压成 BC1/BC3，PSNR 为 41–43.5 dB。其余通道直接写常量：
  - 法线：平面 `(128,128,255)`；
  - ao：白；
  - 高光 s：36–48；
  - 光泽 g：64–110（落在原版布料范围内，偏哑光）；
  - 金属 / 遮罩：0。
