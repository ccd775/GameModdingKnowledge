# L4D2 角色替换 Mod：原则与证据等级

本文是公共知识库的入口规则。它面向后续接手角色替换项目的 agent，目标是减少错误继承、错误类比和“静态检查通过但游戏内失败”的情况。

## 1. 范围

这里记录的是 Source 1 / Left 4 Dead 2 的玩家角色替换流程，重点包括：

- 自定义角色模型、贴图、骨架、动画与第一人称手臂；
- 表情、眼睛、附件物理、布娃娃碰撞；
- Boomer bile、夜光、透明材质等 L4D2 特有材质行为；
- StudioMDL 编译、HLMV 预览、VPK 打包、回滚和实机反馈闭环。

知识库同时保留多个 Karin、Cloth04 和 Riptide 项目案例，但案例中的骨数、位移、材质数量、文件数量等都不是通用常量。

## 2. 三种“正确”必须分开

一个角色替换模型只有同时满足以下三层，才算完成：

1. **接口正确**：路径、ValveBiped 公共骨骼、附件、命中盒、序列、材质槽、第一人称接口等符合目标 survivor。
2. **角色保真**：原角色的身体比例、头肩关系、鞋跟形态、服装轮廓、表情和附件运动没有被错误地改成原版 survivor 的外形。
3. **运行正确**：游戏内动画、落地、武器、受击、Boomer bile、夜光、透明、LOD 和布娃娃都按预期工作。

不要用其中一层的成功代替另外两层。例如，MDL 能加载不代表比例正确；VMT 静态闭包正确不代表 bile 在额外 shader pass 上可见；HLMV 标题显示目标路径也不代表它加载的是自定义二进制。

## 3. 证据等级

遇到冲突时，按下列顺序判断。越靠后越接近最终事实：

1. **游戏分支的原生资源与公开引擎源码**：解释接口和 shader 行为。
2. **已知可用的同类社区 Mod**：证明某种工程做法在 L4D2 中可行。
3. **源文件审计**：Blend、VRM、FBX、贴图和参考 VPK 的结构与哈希。
4. **派生资产静态验证**：SMD/VTA/VMT/VTF/QC/MDL/VVD/VTX/PHY/VPK 的结构、校验和与闭包。
5. **HLMV 可视检查**：绑定、动画、命中盒、物理、材质和落地的快速检查。
6. **L4D2 实机反馈**：最终裁决。截图、录像和复现步骤都应归档。

实机证据推翻静态推断时，先承认静态验证器的覆盖缺口，再修复实现和验证器，不要把运行异常解释为“用户环境问题”。

HLMV 是工具证据，不是必然可用的真理。如果锁定控制组与候选在同一工具模块/位置共同失败，可将 HLMV 标记为 unavailable，并用 compiled decode、CPU skin 和非空离线渲染补足发布前门；实机状态仍不能因此升级。

## 4. 三类参数标签

所有 SOP、报告和脚本参数应明确属于哪一类：

- **通用规则**：例如 L4D2 必须用同一游戏分支的 StudioMDL 编译。
- **项目实测值**：例如某个角色最终有 126 根骨、某个 pelvis 修正为 2.75 Source units。
- **待实机验证假设**：例如某个透明 shader 组合可能兼容，但尚未在游戏内证明。

绝不能把项目实测值硬编码为通用标准。后续项目必须从自己的审计报告重新计算。

## 5. 权威来源分工与合同解耦

制作过程中通常需要三类参考，各自职责不同：

| 来源 | 主要用途 | 不应直接继承的内容 |
| --- | --- | --- |
| 当前游戏安装中的目标 survivor | 模型路径、公共骨骼接口、附件、命中盒、第一人称、HUD、物理等槽位接口 | 原版身体比例；也不能仅由输出槽位推断动漫角色的动画基准 |
| 同角色或相近角色的成熟社区 Mod | 角色静止骨架、比例、附件链、特殊材质和编译技巧 | 文件名暗示的 survivor 身份、陈旧元数据、未验证的 QC |
| 用户提供的 Blend/VRM/FBX | 网格、形态键、原始 UV、材质意图、物理意图 | 未经审计的单位、约束、导出设置 |

参考 Mod 的路径或名称可能撒谎。必须从 QC、骨骼、二进制元数据和实际资源内容判断其真实接口。

每个项目必须分别锁定并报告：

1. output/replacement slot；
2. slot interface contract；
3. character bind/rest skeleton；
4. primary animation family；
5. proportion corrective baseline；
6. ordered sequence/include contract；
7. ground correction owner。

每个独立编译目标还必须分别声明 `visible_geometry_source` 与 `abi_source`。世界模型和第一人称手臂可以共享角色外观，却使用不同 rest/interface；“骨架兼容”不能证明可见网格来自用户源，“目标路径正确”也不能证明 ABI 或动画基准正确。第一人称手臂还应单列 `geometry_selection_source`、`weight_guidance_source` 和 `material_source`。

在本知识库管理的动漫风格/动漫比例 **survivor 替换**中，如果没有另一套已由成熟
参考、编译后二进制和游戏实机证明的动画合同，默认且强制使用 Zoey/TeenAngst 作为
主动画与 corrective 基准。Louis/Rochelle 等只表示输出槽位时，禁止据此自动选择
Manager/Biker/Producer rest。该默认不适用于 Hunter、Witch 等 non-survivor；它们
必须锁定当前目标槽位或已验证同槽位参考的 animation/corrective/sequence 合同。详见
[槽位、动画基准与 Zoey/TeenAngst](15-animation-basis-slot-and-zoey.md)。

## 6. 不可破坏的工作约束

- 对所有输入文件和关键工具建立 SHA-256 锁；每个会改数据的阶段前重新验证。
- 不在用户原始 Blend/VRM/FBX 上直接操作，只创建命名明确的派生文件。
- 编译到隔离的 `gameinfo.txt` 沙盒，不写入正在使用的游戏目录。
- 构建输出写到新目录并拒绝覆盖旧候选；旧候选保留但标记为 superseded 或 rejected。
- 用候选清单指定“当前交付件”，不要从目录中所有 `.vpk` 猜测最新文件。
- 所有自动化都输出机器可读 JSON 和简短 Markdown 摘要；关键截图保留原图。
- 用户要求手工实机测试时，仍完成静态验证，但明确写“未执行游戏内自动化测试”。
- 新回归器同时锁定修复候选和已知坏候选：前者通过，后者按预期 check ID 失败；避免空集合和恒通过门禁。
- 发布 manifest 是不可变打包快照；发布后的用户 pass/fail 以 VPK SHA 绑定的 append-only runtime evidence 追加。

## 7. 后续 agent 的进入协议

接手项目时按顺序执行：

1. 阅读本文件和 `README.md`。
2. 阅读端到端 SOP，确定当前阶段及前置门槛。
3. 阅读项目自己的 `PROJECT_STATE.md`、source lock、最近一次候选清单和失败记录。
4. 只读取与当前问题相关的专项手册；不要无目的地重跑全流水线。
5. 验证当前输入、工具版本和候选哈希后再修改。
6. 每次修复都同时更新：source-of-truth、派生产物、验证报告、候选清单、状态文档。

## 8. 核心决策原则

- 保持角色原始形象，借用的是 survivor 的动画接口，不是 survivor 的身体形状。
- 不从 `$modelname` 或 survivor 名字推断动画基准；槽位、rest skeleton、动作族和 corrective source 分别决策。
- 先证明接口和数据流，再做视觉微调。
- 引擎会自动完成的变换不要提前再做一次。
- 任何“看起来像”的方案都必须能由哈希、结构检查或运行证据定位到具体输入。
- 在 L4D2 中，简单且在主 shader pass 内完成的材质路径通常比附加 pass 更可靠。
- 不隐藏警告。所有警告都先视为失败，直到被分类并有证据说明可接受。
