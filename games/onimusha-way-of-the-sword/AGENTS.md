# Agent 入口（Onimusha: Way of the Sword）

先读 [README](README.md)，再按当前问题进入对应文档。项目的当前状态在独立工程的
SOP，不在这里；本目录只提供方法和已被证伪的假设。

## 接手一个新任务前

1. 核对 Steam appmanifest 的 build / depot / manifest。**build 变了，本目录所有具体
   版本号、偏移、骨数和参数都要重新提取验证。**
2. 反推当前 build 的 Mesh / GPUC 扩展名，并确认工具适配层已显式声明它们 ——
   插件的「版本近似」是静默的。
3. 确认这一版要改的是**几何**还是**物理**，两者的验收口径不同，不要在同一版里混改
   之后归因不清。

## 硬性规矩（本项目已付过学费）

- **不要修改已冻结的生产构建器。** 扩展走运行时注入的版本化 runner。若已经改了，
  必须还原并用「重跑上一版、产物 SHA-256 逐位相同」来证明还原是行为等价的。
- **不要放宽冻结闸门。** 先开探针跑打出实测值，只重定基被证明必须重定基的那一项；
  数值公差越界时分集合给上限，不整体放宽。
- **不要跨链族搬运物理档位。** 默认是从原生出发、只改已证明必须改的。
- **不要把左右差异当数据缺陷查**，除非已做过逐字段穷尽比对。角色动画本身就不对称。
- **不要用退出码判定 Blender 无头构建成败。**
- **不要声称实机通过。** 离线闸门全绿、部署 parity 通过、确定性双跑通过，都不等于
  玩过。同一个包里不同改动的验收级别不同时逐项分层写，并同步改到打包器打印、
  release report 和随包 README 三处。
- 交付前跑**部署一致性闸门**（stage 与游戏 `natives/` 路径集合双向相等 + 逐文件
  SHA-256 相同）。它拦下过「只更新了第一套服装、而实机渲染的是第二套」。

## 报告口径

结论要能被归到 `invariant` / `build-sensitive` / `case-derived` / `hypothesis` /
`rejected` 之一。历史失败不删除；后来的证据只用于**收窄**旧结论的适用范围，并显式
写明 supersedes 关系。
